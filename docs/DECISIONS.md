# Decision log

## ADR-001 Course-first, not AI-first — accepted 2026-11-10
Use established human-written courses as the primary means of teaching new concepts. There is no generative LLM required or trusted as a correctness/education authority. Engine analysis supports concrete evaluations only.

## ADR-002 Protected-course link strategy — accepted 2026-11-10
Chess.com and Chessreps memberships provide access within the providers' interfaces. Without permission or authorized exports, link out and track completion/independent checks; do not scrape or mirror copyrighted courses. The cost is weaker integrated/offline lessons; mitigate with rights-cleared materials and explicit UX.

## ADR-003 Offline-first data, delayed sync — accepted 2026-11-10
Installable iPhone PWA with IndexedDB local progress; Mac native batch engine. Optional static hosting may deliver app shell and rights-cleared packs but cannot receive personal progress in phase 1. Explicit backup/restore is non-negotiable.

## ADR-004 Measurable performance — accepted 2026-11-10
Display separate ratings, unseen practice, reproducible game error metrics, concept mastery and cross-context transfer with denominators and source drill-down. Don't combine them into an arbitrary skill number.

## ADR-005 Deterministic scheduler first — accepted 2026-11-10
Use prerequisites, transparent priorities and memory scheduler; only introduce statistical personalization when sufficient real evidence exists, preserving unknown/uncertain states.

## ADR-006 Scope limited to one learner — accepted 2026-11-10
No login required initially, no payment system, no multiplayer/community, no shared cloud infrastructure. Private, simple, maintainable code wins over extensibility theater.

## ADR-007 Lichess board and rules libraries; project licensed GPL-3.0-or-later — accepted 2026-11-10
`@lichess-org/chessground` 10.5.0 (touch board; the unscoped `chessground` package is deprecated) and `chessops` 0.15.1 (single authoritative rules library: legality, FEN, SAN, castling, en passant, promotion, mate). Both are GPL-3.0-or-later, so this repository is GPL-3.0-or-later and any public hosting must offer the source. Alternative considered: `react-chessboard` + `chess.js` (MIT/BSD), rejected because chessground's touch handling and chessops' Lichess-compatible semantics matter more to a single-user app than licence permissiveness.

## ADR-008 Toolchain pins — accepted 2026-11-10
Node 22.23.1 (`.nvmrc`; the machine default 21.x cannot run Vite 8), React 19.3.1, Vite 8.3.7, TypeScript 7.0.2, Vitest 5.1.0, Playwright 1.65.0, Dexie 4.4.7, vite-plugin-pwa 2.0.0. `ts-fsrs` is pinned at 5.4.2, not 6.0.0, because 6.x requires Node 24 for tests; 5.4.2 already implements FSRS-6. Python 3.13 via `uv`, python-chess 1.11.2, native Stockfish 19.

## ADR-009 Local lessons are verbatim public-domain excerpts, proven mechanically — accepted 2026-11-10
Offline lessons use only text that is public domain (Edward Lasker 1918, US only; Capablanca 1921) or otherwise cleared. The app stores unaltered excerpts; `pipeline/trainer_pipeline/lessons.py` fails the build unless each paragraph is a substring of the checksummed source file, each diagram matches the book, and each move is legal and within 5 expected-score points of Stockfish's first choice. Interface prompts around a lesson are limited to facts the rules library can state ("White to move"). Cost: 1918 prose and notation, and thin coverage (see `docs/CONTENT_INVENTORY.md` §2). Excerpt selection was done by the build agent, so every lesson carries `ownerReview: pending` and the UI says so until the owner approves it. The Lasker text is cleared for the US only; a non-US owner must remove it.

## ADR-010 Puzzle answer policy and pack gate — accepted 2026-11-10
A puzzle answer is correct if it is the source move or any move that delivers checkmate (Lichess's documented rule). Everything else is scored as a miss. To make that safe, a puzzle is only shipped if Stockfish 19 (150k nodes, MultiPV 2, 1 thread) agrees at every solver move that the source move is the first choice and at least 20 expected-score points better than the second. Puzzles failing the gate are dropped, not shipped as "ambiguous". The UI therefore says "not the move" rather than "bad move", and cites the engine check.

## ADR-011 Evidence model: unseen first tries only — accepted 2026-11-10
An attempt's outcome is decided once, at the first of: wrong move (fail), hint or revealed solution (assisted), clean solve (success), or leaving before moving (skipped). `fresh` (first-ever showing) and `scheduledReview` are stamped at write time. Unseen accuracy counts fresh puzzle attempts only; assisted counts as not solved; skips are excluded and reported. Rates are shown as k of n with a 95% Wilson interval and are "provisional" below n=20. Concepts with no observations are "untested". The practice-difficulty estimate is an Elo-style number on the Lichess puzzle scale used only for selection.

## ADR-012 Concept stages and the check rubric — accepted 2026-11-10
`new → started → taught → demonstrated`, derived from lesson events. "Taught" is a finished local lesson or a self-reported linked lesson; opening a link is recorded but proves nothing. "Demonstrated" requires check-v1: 5 never-seen puzzles on the concept, Lichess rating 900–1299, no hints, 4 solved first try. Passing without a lesson is a pre-test skip. Prerequisites are advisory in the UI (nothing is locked) but the planner follows them. A fixed band, not the learner's own level, keeps "demonstrated" meaning the same thing over time.

## ADR-013 Review scheduling — accepted 2026-11-10
FSRS via ts-fsrs with fuzz off, short-term steps off, retention target 0.9 and a 365-day cap. Missed puzzles and all lesson examples enter the queue; success is Good, a miss or hint is Again. Review state is a pure fold over the immutable attempt log (`rebuildReviewStates`) and carries the scheduler version, so a scheduler change never rewrites history.

## ADR-014 Chess.com access posture — accepted 2026-11-10, two items awaiting the owner
The app never requests `www.chess.com`. Linked lessons are stored as title, author, level and URL only. Own-game import (M4) defaults to manually downloaded PGN. Open for the owner: (a) whether to keep the lesson links first collected by the automated audit or re-collect them by hand, given User Agreement §4(D); (b) whether to add a serial PubAPI fetch script for own games.

## ADR-015 Baseline is a sampler, not a score — accepted 2026-11-10
The first-run diagnostic shows two unseen positions for each of the 15 early concepts that can be assessed with positions (prerequisites ignored), choosing the least-sampled concept next. Its progress is derived from the attempt log (any unseen attempt counts), so it has no state of its own and resumes anywhere. It can only produce "untested", "provisional" or "pre-test to skip"; the 5-position check decides demonstration. A position counts for every concept whose theme tag it carries.

## ADR-016 Play days and the game journal (schema 2) — accepted 2026-11-10
A play day replaces the four study blocks with warm-up review, one 10+5 game on the learner's own site, and a written reflection. Suggestion rule v1: play after two study sessions since the last play day, never more than two play days in seven; always overridable. The game is logged by hand in `gameJournal` (schema 2: result, colour, own-words notes, optional rating and link; the link is stored and never fetched). Backups are schema 2 and still restore schema-1 files. The app writes no chess advice on the play screen. The projection in Learn assumes Wednesdays and Saturdays; real suggestions follow the rule above.

## ADR-017 An engine disagreement demotes a lesson example from "asked" to "shown" — accepted 2026-11-10
When the validator finds the author's move more than 5 expected-score points below the engine's first choice, the learner is not asked to find it; the position and the author's explanation are still shown verbatim. The text is never edited to agree with the engine, and the engine's preference is not presented as instruction.

## ADR-018 Opening repertoire: the learner's own moves, ordered by real frequency (schema 3) — accepted 2026-11-10
Chessreps has no export and its lines may not be copied, so the repertoire trainer stores only what the learner enters: for a position where it is their move, the move they have chosen (`repertoire` table, keyed by side + `positionKey`, so transpositions are one decision). The app contributes evidence, not choices:
- **Frequency**: `public/packs/openings-lichess.json`, built by `pipeline/trainer_pipeline/opening_stats.py` from the first 1.5 GB of the Lichess October 2026 rated-games dump (CC0; the explorer API needs a token). Rated blitz/rapid/classical only, each move banded by the mover's rating, full tree to 4 plies and to 14 plies under 1.e4 e5 and 1.e4 c6. The learner picks the opponent rating band; the next position to record is always the unanswered one reached most often.
- **Engine**: `opening_evals.py` stores Stockfish's expected score after each listed move and for its own first choice. A chosen move within 8 points is "sound", further is "weaker" (shown with both numbers and the first choice's name; the learner may keep it), and a move without data is "unknown", never "bad".
- **Recall** is a disclosed recall mode on FSRS: only the chosen move counts as recalled; a different move is recorded with `altVerdict` (sound / weaker / unknown) and reported separately on Progress, not as a blunder.
- **Preparedness metric**: share of games (in the chosen band) with a recorded answer at the learner's k-th move, with the shares that have no answer or fall outside the data shown beside it. It measures what is recorded, not board performance.
Limits: the sample is the start of one month, not a random sample; data is deep only under two first-move families; Lichess rating bands are not Chess.com ratings.

## ADR-019 Own games: manual PGN in, Mac analysis, file import; conservative labels (schema 4) — accepted 2026-11-10
- **Import path**: the owner downloads PGN from Chess.com by hand; `pipeline/trainer_pipeline/games.py` parses it (side, result, ratings, time class from `TimeControl` using Chess.com's own boundaries, `%clk` clocks) and never contacts a chess site. Games are identified by a hash of the site's game link, so re-imports are idempotent. A PubAPI fetcher is not built (owner decision pending, ADR-014).
- **Analysis**: Stockfish 19, 200k nodes, MultiPV 2, one thread, only at the learner's own moves. Expected score is the Lichess win% sigmoid from the learner's side. Rules, all recorded in the file manifest: major error = loss >= 20 points; label "allows mate" (mate in <= 3 for the opponent) or "loses material" (>= 2 points within 5 half-moves of the engine's reply line), otherwise "unclassified"; tactical opportunity = the engine's best line mates or wins >= 2 points within 5 half-moves; missed when the move played gave up >= 10 points; a position becomes a personal drill only when the best move beats the second best by >= 20 points. No label states why a move was played.
- **Transfer to the phone**: one JSON file (`data/analysis/my-games.json`, git-ignored) imported under Progress, Your data. Private game data is never published to static hosting.
- **App**: `games` table (schema 4, in backups). Re-analysis with different engine settings replaces the stored analysis and is labelled by `analysisKey`; mixed settings are called out on the card. Metrics: rating after each game per time control; major errors per 100 analysed decisions with Wilson range, per game and per time control; missed chances out of chances available; errors under 10% of starting time versus otherwise, shown only with 30 decisions in each group. Unanalysed games are excluded from denominators, never counted as clean.
- **Drills**: own-game positions are recalled through the same FSRS queue (`exerciseKind: 'own-game'`); they are never counted as unseen puzzles.
Not built: training-to-game transfer metric (needs dated drill history against later games), PubAPI fetch, analysis of opponents' moves.

## ADR-020 Exact king-and-pawn endings from a table computed here — accepted 2026-11-10
`pipeline/trainer_pipeline/kpk.py` computes, by level-synchronous retrograde analysis with python-chess as the move generator, the result of every K+P v K position and the number of half-moves to a safe promotion with best play (`content/kpk.json`, 279 kB, bundled). It is validated against known theory (including Lasker's "only by playing K-e5"), the published count of 111,282 won positions for the pawn on files a–d, Stockfish on a random sample, and the property that best play shortens the distance by exactly one per half-move; the app-side probe is tested against the same properties. No Syzygy download or tablebase API is needed for this ending.
The app uses it for play-outs: "win it" against the longest defence and "hold it" against the most testing tries, from 480 start positions in which exactly one move keeps the result. Every learner move is judged by whether it changed the theoretical result, so feedback says "lets the win go" or "loses" as a fact and lists the moves that kept it; nothing is engine opinion. A win must be converted within 30 moves and a draw held for 10. Results feed a separate "Endgame technique, exact" metric and the review queue, never the puzzle metric.
Still open in M5: basic mates and rook endings (need larger tables or Syzygy), exchange-counting drills, deeper calculation training, the training-to-game transfer metric, and a controlled evaluation of scheduler changes.

## ADR-021 "The opposition" is checked by exact play-outs; scheduler forecast is compared with outcomes — accepted 2026-11-10
- `endgame.opposition` no longer uses puzzles tagged "pawn endgame" as its check or its evidence. Its check is check-kpk-v1: five unseen king-and-pawn starts (three to win, two to hold) against perfect play, no help, four must be kept correct on every move. Its evidence is first-time play-outs. `endgame.passed-pawn` still uses tagged puzzles.
- `reviewCalibration` replays the attempt log and, at each scheduled review, compares the recall probability FSRS predicted just before it with the outcome. The retention card shows forecast against observed with n. This is the baseline any later scheduler version must be replayed against on the same log before it replaces v1. Note from building it: after a first miss the earliest review is one day later, which FSRS itself forecasts at about 77%, below its 90% target for established items.

## ADR-023 Game analysis v2: chances and labels measured on whole lines — accepted 2026-11-10
Running v1 on the owner's 87 real games showed two faults in the labels. v2 fixes them: a tactical chance needs the engine's best line to end at least two points up on the balance before the opponent's last move, so taking back a piece is not a chance; "loses material" means the line after the move played ends at least two points down on the balance before that move, so an even trade is not a loss; a new label "misses material" covers a major error where nothing is lost but the best line would have won at least two points more. Files carry `analysisVersion`; the app replaces a stored analysis when the version or engine settings differ.

## ADR-026 Games and ratings refresh themselves; analysis also runs in the app — accepted 2026-11-10
The owner asked that nothing about the app need a manual step ("does this automatically import all data … I don't want to have to do anything manual"). Until now the answer was no: games were fetched and analysed on the Mac and carried over as a file. This supersedes the sentence "the app still never contacts chess.com" in ADR-022 and the file-only import of ADR-019.
- When the app is opened or brought to the front (at most every three hours, or on "Refresh now") it reads the owner's public profile statistics and monthly game archives from Chess.com's Published-Data API directly from the device: documented endpoints only, strictly one request at a time, conditional requests, stop on 429, months already read are not read again except the current one. Requests carry no cookies and no referrer. The API allows cross-origin reads; this was confirmed from WebKit and Chromium on the published origin. No server of ours is involved and nothing else leaves the device.
- New games are analysed on the device by a vendored Stockfish 19 "lite, single-threaded" WebAssembly build (GPL-3.0, `public/engine/`, provenance recorded there), with the same rules as the Mac pipeline (analysis v2) at a fixed node budget. It runs only while the app is visible, newest game first, and resumes where it stopped.
- Each analysis records its engine and node budget, and the games card names the engine behind its numbers. A deeper Mac analysis becomes the analysis to look at for that game; the device's own analysis is kept beside it as the measurement record (ADR-032).
- The Chess.com handle is a preference stored on the device. The published build can carry a default handle from the git-ignored `data/deploy.env`, so the owner's phone needs no setup; the handle is then visible in the public bundle (it is the owner's public handle). It is not in the repository.
- Ratings shown are the ones Chess.com reports, with the time they were read. They are not turned into any other score.
- Failure states are explicit: offline, rate-limited, unknown player, other error; the last successful data stays in place.
The Mac pipeline and file import remain as an optional, deeper path.

## ADR-027 One game measure fixed in advance; missed chances counted where the game was still open — accepted 2026-11-10
An outside review (and an audit of the owner's 87 analysed games) found the games card flattering and unfocused. Changes:
- The headline is fixed before looking at future data: the share of rated rapid games that contain an avoidable loss of material or allowed mate within the first 20 moves, shown as the last 20 such games against the 20 before, with counts and its plausible range. Time controls are never pooled; unrated games and games against bots are left out. Its exact definition and the engine setting behind it are in ADR-032.
- "Chances missed" leads with positions that were not already decided (expected score before the move under 90), because converting a won game by another route is not a miss; the all-positions figure stays beside it.
- Clock pressure uses the clock before the move was made, not after.
- Hinted solves no longer feed the level estimate.

## ADR-028 Questions from the owner's own games: "is this move safe?" and "is there something here?" — accepted 2026-11-10
Both reviews found the largest group of the owner's real errors (about a third) to be one-move piece-safety failures, and that puzzle practice does not train noticing them, because a puzzle announces that something is there. The app now builds two kinds of question from analysed own games: a move that was played is shown and the learner says whether it is safe (then shows the punishing reply), and a position is shown and the learner says whether there is a clear chance (then plays it). Half of each kind are controls where the honest answer is "safe" / "nothing special", so always answering yes scores badly. Positives and controls are defined by the same test (ADR-032); truth comes only from stored engine analysis with fixed margins; a reply the stored analysis cannot judge is checked by the device engine, and if that is unavailable the answer is recorded as unverified, never as wrong. Hit rate on real items and the rate of false alarms on controls are reported separately. No explanatory text is written by the app. These alternate with puzzles in the unannounced test block and can be practised on their own.

## ADR-029 Checks are delayed, do not announce their theme, and are asked again — accepted 2026-11-10
Both reviews objected that a concept became "demonstrated" for good after five single-theme puzzles taken minutes after its lesson. Now: inside a session a first check is never given on the day the lesson was studied and needs at least six hours in between (a lesson at 23:55 is not checked at 00:05), and the concept that has waited longest goes first; while it runs the check does not name its concept (the result does); a passed check is asked again after 21 days. A demonstrated concept whose pass is stale, or whose re-check was not passed, is labelled as such. It keeps unlocking what depends on it, because revoking that would lock lessons already begun. The check on a concept's own page stays available at any time as the learner's choice. Fixed alongside: the five positions of a check are drawn once (they used to be re-drawn after each answer and could run out mid-check), and a check position cannot be skipped.

## ADR-030 Review rules after the audits — accepted 2026-11-10
- Due means due today (local calendar day), not "24 hours later to the minute".
- A repertoire drill is identified by position and move. Changing the move for a position starts a new item; states saved under the old position-only id are no longer offered and the position is recalled once more under its new id. Attempts are never rewritten.
- Castling is stored and looked up in one spelling.
- A position that was shown and left is recorded as skipped (so it can never count as unseen later); skipped showings do not reset "days since last seen".
- The apply block only targets concepts that have a puzzle filter; a concept checked by play-outs used to receive arbitrary puzzles.
- A session opened and left untouched does not count toward the play-day suggestion.

## ADR-031 Session identity, atomic session writes, preferences in backups, promotion in K+P v K — accepted 2026-11-10
- The running session is found by its state: an unfinished session of today, or one from yesterday still in use within the last three hours. A session in progress at midnight no longer disappears, and no empty row is written.
- Session changes are read-modify-write inside one transaction, so a clock tick and a recorded attempt cannot overwrite each other.
- Backups carry the learner's preferences (opening band and side, lesson positions, Chess.com handle) in an optional, checksummed section; device bookkeeping is not carried; a preference already set on the receiving device is kept. Every earlier backup file still restores.
- King and pawn endings: promoting to a bishop or knight, or to a queen that stalemates or can be taken, is a draw and is scored as one; when holding a draw the app's side never promotes into a capture while another move exists, and a play-out that leaves the ending ends cleanly.
- The board is measured again at the start of every touch. It used to keep its old screen position when something above it appeared, so a correct tap could be recorded as a different, wrong move.

## ADR-032 One measurement record per game; the target defined on the board; controls that mean something — accepted 2026-11-10
The outside reviewer's second pass found three faults in ADR-026 to ADR-028 as first built. All three were real.
- **A changing mix of engines would have faked a trend.** Older games analysed by the Mac's full engine and newer ones by the phone's small engine are not the same measurement. Every game now gets a measurement record: the app's own analysis (analysis v3, the vendored engine, one node budget, a fresh engine state for each game), stored beside whatever other analysis the game has. An imported Mac analysis is what you look at when reviewing a game; it never replaces the measurement record. The headline number reads only measurement records of one engine setting, names that setting, and reports games still waiting as pending. Changing the setting means re-measuring both comparison groups, not mixing.
- **The headline still depended on the score scale.** A "major error" needs a 20-point drop in expected score, and that scale flattens out in positions already won or lost: a piece hung there barely moves it. The target is now defined on the board. Analysis v3 records for every decision the expected score before it and the material balance at the end of the short line after the move played and after the best move. A target event is a move that allowed an avoidable mate in three or fewer, or lost at least two points of material that the best move would not have lost. One exception: in an undecided position (expected score 10 to 90) a move the engine rates within two points of best is a sacrifice it accepts, not an event. Beside the per-game share the card shows every such move per decision in the same move range, because "at least one per game" cannot show three mistakes becoming one. Known limit: a sound sacrifice in a position that is already decided is counted.
- **Some "safe" and "nothing special" controls were not.** A move that hung a piece in a lost position cost under three points and could be offered as safe; a position with two winning captures could be offered as nothing special. Now a safe control must lose less than two points of material in its line, allow no quick mate, cost at most three points, and come from an undecided position; a "nothing special" control needs a best line that wins less than two points of material and is not a mate. Forced losses, costly moves that lose no material, and positions with several winning moves are not asked at all. Questions are built only from measurement records.
Also from that pass: games actually played (fetched rapid, blitz and bullet games) count as play days whether or not a play session was logged; after a wrong puzzle move the built-in engine's reply can be shown on request, labelled as the engine's line and not as an explanation; a forced "Refresh now" is never dropped while a background round is running.
Not taken up: showing detection as d-prime (the reviewer advised against it at these sample sizes); a self-generated "choose a move, predict the reply, keep or revise" drill, which is the reviewer's recommended next format and is the next slice.

## ADR-033 After the data-validity audit — accepted 2026-11-10
An audit that re-ran the game pipeline on the owner's 87 games and read 53 labelled positions by hand found the following. What was changed in the app:
- **The same game did not get the same analysis twice** (5 of 87 identical between two runs): the engine's memory carried over from whatever was analysed before. The device now clears the engine before every game, and a test analyses one game twice with another in between and requires identical records.
- **Material verdicts were read off lines cut short in the middle of an exchange.** The device parser already ignores unfinished search results (bounds). In addition a line that stops right after a capture, or with captures still going on at the cut-off, is marked unsettled: such a decision is neither a target event nor a "nothing here" control.
- **Unrated games were treated as rated**: PGN files do not say, and an unrated game often carries the rating of another time control. Games fetched by the app carry the flag; a sync now also fills it in for games that arrived as a file; unrated games are left out of the rating series as well as the headline.
- **"Missed chances" mostly counted positions with nothing to find** (several moves winning about as much), and counted one chance again on every move it stayed available. The card now leads with chances that had one clearly best move (20 points over the next), each counted once and missed only if never taken.
- **The clock card pointed the wrong way**: most low-clock moves come in games already decided, where a major error is impossible. Only undecided positions are compared (from the measurement record), with the clock before the move.
Not changed, and still true of the Mac pipeline (`pipeline/trainer_pipeline/games.py`, analysis v2), which is now only the optional deeper view of a game and feeds no trend, question or headline: it does not clear the engine between games, it accepts unfinished search results, it has no "missed mate" label, and PGN downloads carry no rated flag. Also open from that audit: 10 of 27 lesson moves have another move within five points (a learner playing it is told it is not the text's move, which is true, but it is scheduled for review as a miss); one puzzle counts toward 2.4 concepts on average; Wilson intervals on decisions ignore clustering by game (the headline uses games as its unit; the secondary cards do not); the opening "sound" margin of 8 points is lenient.

## ADR-034 Owner decisions of 2026-11-10 (second set): phone only, offline on the subway, practice-heavy session — accepted
The owner answered the open questions. This narrows the product contract ("one user, iPhone and Mac" becomes one user, iPhone) and supersedes ADR-019's file import, the Mac half of ADR-022, and M6.
- **Phone only.** The Mac game route is removed: `pipeline/trainer_pipeline/games.py`, `fetch_chesscom.py`, their tests, and the in-app import of an analysed-games file. Games arrive only from Chess.com's public API and are analysed on the device. The loader for the hand-checked games fixture survives as test support (`src/games/fixtures/load.ts`). The rest of `pipeline/` stays: it builds what the phone downloads (puzzle pack, lessons, opening book, endgame table). Sync between devices (M6) is dropped; a backup file remains the way to keep a copy.
- **Offline on the subway is a hard requirement**; most sessions will happen there. Everything except fetching new games and opening linked lessons must work with no network, including the engine. A browser test now covers a cold start with no network followed by a whole session: stored games, a refresh that says plainly it is offline, an on-device lesson, own-game questions with feedback, puzzles, and the engine's reply to a wrong move. Consequence: on-device lessons for the first concepts are now the main content gap, because a linked lesson cannot be studied underground.

## ADR-037 One-button practice; the board stays with the lesson text — accepted 2026-11-10
The owner asked for "a single button that brings me into whatever I need to practise ... I shouldn't have to think about what to do and it should effectively train me best", without knowing in advance what kind of thing is coming.
- **"Just practise"** (on Today and at the top of Practice) runs an open-ended mixed stream. Policy mix-v1 (`src/schedule/mix.ts`): each turn is one of four kinds, drawn by weight from those that have something to offer: something due again (3), a question from his own games (3), an unseen position on the concept with the least evidence so far (3), a position from his own games where one move was clearly best and he played another (1). The same kind never comes three times running while another is available. Every item carries the same heading ("Practice"); no concept, theme or exercise type is announced, and puzzles are given with no hints. Each turn's item is chosen once and kept. Everything is recorded as ordinary practice: a first try on an unseen position counts as evidence, repeats do not. There is no timer and no fixed end; it stops when the learner stops or nothing is left. The weights are a first policy, to be revised with the outside reviewer's answer.
- **Due reviews are taken in order of worth**, here and in the session's review block: positions from the learner's own games first, then lesson examples, repertoire moves, endings, puzzles; longest overdue first within each.
- **In lessons the board stays at the top of the screen** while the text is read beneath it, and a page of text shows the position it is about (the board just shown, or the one that follows). Text and diagram used to be on separate screens, and on examples with a long lead-in the board started below the fold.
- From the outside reviewer's third pass (interim): the coin toss that decides whether a question has something in it was tied to the even/odd turn number through the hash's lowest bit (early "safe?" questions were all controls); the hash now has a final mixing step. A move that wins material but allows a forced mate was accepted as a chance taken; a forced mate for the other side now makes the answer wrong, and a chance taken must leave the learner at least level.

## ADR-038 After the outside reviewer's third pass: evidence, the stream, the queue — accepted 2026-11-10
The reviewer read the pushed code (commit 0d6a3b4) and ran its own probes. Its central objection: one engine continuation was still being treated as proof. Changes:
- **What a line can show** (analysis v4; every game is measured again). A line's material balance is relied on only when the line runs the whole five-ply window and then continues with a quiet move, or the game ends inside it. A line that runs out early, has no moves, or stops on a capture or a promotion is not settled (a promoted queen that is taken next move used to count as settled). Material given up at no cost to the engine's score is a sacrifice in any position, decided or not, and is not counted as an error or asked as "unsafe". An engine that returns no line for a position no longer yields a clean-looking analysis: the game stays unmeasured and is tried again.
- **Own-game questions.** A forced mate decides before material, using the engine's own mate score (taking a rook while allowing mate in one was accepted as a chance taken). A chance is asked only with a second move to compare, a settled line and a clear margin, or a mate in three or fewer. Saying "there is something" is now always followed by playing the move, on control items too, so the screen no longer gives the answer away, and a learner who proves a control wrong is not charged a false alarm (the item is not scored). Both sorts must be available or nothing is asked. The coin toss that picks which comes first no longer follows the turn number.
- **The headline compares fixed groups.** The latest 20 eligible games and the 20 before them are fixed by date first; while any of them is unmeasured no comparison is shown (an older game used to be slipped in).
- **Sync.** The two newest months are read on every pass (Chess.com's answer for the month just ended can be stale when first re-read). Requests time out after 20 seconds, and analysis of games already on the device no longer waits for the network.
- **One-button practice, mix-v2.** The reviewer's starting shares: due review 25, "is this move safe?" 30, "is there something here?" 10, own missed moves 10, puzzles 25 (half on what is being learned now, half on the least-tested concept). A natural end after 20 minutes at the end of an item, with the offer of five more. Not yet done from its proposal: a persisted seed and frozen item across reloads, exposure recorded before the position is shown, a fifth of source games reserved for assessment, repeats after seven days, controls matched to positives.
- **Review queue, policy v2.** Only a miss enters the queue (a repertoire move always does: recalling it is the exercise). An item recalled after two weeks or more leaves active review and returns if missed again; an item missed four times is set aside. Stored states are rebuilt from the attempt log when the policy changes. This is the reviewer's answer to a backlog that grew to 76 in five simulated weeks; its other proposals (one card per position family, an admission budget while the backlog is large) are not built.
- **Not built, and the reviewer's main point:** the biggest remaining obstacle is the gap between recognising a tactic that is put in front of him and checking a move he himself intends to play. The exercise for that ("choose a move, name a reply you must reckon with, optionally revise", graded with abstention: only exactly verifiable failures count, everything else is evidence to look at) is the next slice, as are checks that test the operation itself (which piece can be captured after this move; the net of an exchange; is there a check, capture or mate).

## ADR-039 "Your move": the learner's own move, checked by exact facts — accepted 2026-11-10
Every reviewer, and the outside reviewer most plainly, named the same gap: the app trained recognising something that is put in front of the learner, while his games are lost on moves he chooses himself (moves 10 to 19, with time on the clock). New exercise (`src/games/ownmove.ts`, `src/ui/OwnMove.tsx`):
- An ordinary position from one of his own games, his move, move 10 to 19, the game undecided; not only positions where he went wrong, and positions of one game at least eight plies apart.
- He plays his move (it is committed at once), then plays the reply he had to reckon with, or says there is none.
- The app answers with facts found by generating legal moves, not opinions: each piece of his that can now be captured and not recaptured, or captured by a cheaper piece (pins respected), and any mate in one. Then the built-in engine's line and score as evidence, and the move he played in the game.
- Graded with abstention, as the reviewer specified. Allowing mate in one is a failure. A loose piece is a failure only if the engine's line also shows a settled loss of at least two points of material and a drop of at least 20 points; a loose piece the engine accepts is not scored. With nothing loose, a move the engine dislikes for other reasons is not scored either. Clean moves are recorded as successes. Whether the reply he named was the one that mattered is recorded separately and is not scored.
- It has its own entry under Practice, takes a quarter of the one-button stream (mix-v3: review 25, your move 25, safe 15, chance 10, missed 5, puzzles 20, the reallocation the reviewer proposed), and a failed position returns in the review queue.
- Not yet: a number for it on Progress; an optional revision step; its use as the check for the piece-safety concepts.

## ADR-041 One loop for the core skills, and a clock that only tightens while moves stay clean — accepted 2026-11-10 (the assistant's design; the outside reviewer's view to be integrated when it arrives)
The owner asked for a design for training under time pressure, and for one elegant mechanism that teaches the core principles. What his clocks show (ADR-040): in rapid he is not short of time, he loses with nearly half his clock unused and makes his errors with time in hand; his daily rating is far higher. So the thing to build is not speed. It is a check on his own move that is reliable first and then quick enough to be used every move of a ten-minute game.
**The pedagogy this rests on**, with how solid each part is:
- *Practise the act itself.* Skill transfers to what resembles the practice. He chooses a move in an ordinary position from his own games, as in a game; nothing is announced. (Well supported in general; consistent with his gap between announced puzzles and games.)
- *Immediate, specific, factual feedback* after every move. (Well supported.)
- *Accuracy before speed.* A routine is made reliable untimed, then made fast; pushing speed first trains fast errors. (Well supported as a principle; the particular thresholds here are guesses.)
- *The clock as exposure.* Doing the check under a visible clock is how the feeling of pressure is worked on. (Reasonable inference; not established for chess.)
- *Mixing and spacing*, and his own failures coming back. (Well supported; already in the stream and the review queue.)
- *Commit before feedback*, including naming the opponent's reply. (Moderate support.)
- *Judge by games*, not by the drill's own numbers.
**The design.**
- "Your move" (ADR-039) is the one loop. After each move the app now reports all three things a move should be checked for, each found by generating legal moves: what of his could already be taken before the move and whether the move dealt with it; what he could have taken and kept, and any mate in one he had; what can be taken after the move, and any mate in one allowed. One act, three facts: safety, the opponent's threat, the chance. Only safety is scored (with abstention, as before); the other two are stated and counted.
- A pace ladder (`src/schedule/pace.ts`): no clock, then 30, 20, 15 and 10 seconds for choosing the move. Ten clean moves in the last twelve at a pace tighten the clock; six or fewer loosen it. The rung is computed from the attempt log. Only the choosing is timed; naming the reply and reading the feedback are not. A move not made in time is still played and still gets its facts, is recorded as not made in time, and counts as not clean at that pace. Nothing rewards being quick: the only way to a faster clock is clean moves. Fifteen seconds is what a ten-minute game allows per move, so that rung is the target and ten seconds is headroom.
- Measurement (Progress, "Your own moves"): clean moves of those established, with range; moves not scored; moves not made in time; how often a threat was dealt with and a free capture taken; how often the reply he named was the one that mattered; the pace reached and the count at it; and from his real rapid games' clocks, how many major errors came with over half the clock left and how much time was unused when games were lost.
- Not built: a bank of time across several moves (budgeting, as in a game); the same clock on puzzles and own-game questions; an optional revision step; a measure of game errors by seconds spent on the move.

## ADR-042 After a first-principles review by a reviewer with no prior context — accepted 2026-11-11

## ADR-043 Owner decision: judge moves harder and say the result plainly — accepted 2026-11-11
After using it the owner said: "practice is too conservative / not clear sometimes. It should judge my moves a bit harder; I clearly miss the best move but it gives me a pass. Also sometimes it's just not clear what my performance was." This changes the abstaining grade of ADR-039 for "Your move", on the owner's authority, and relaxes how the invariant "never score a sound non-book move as objectively wrong" is applied there: the verdict is stated as the built-in engine's rating, with both numbers shown, not as a fact about chess.
- **Every move is rated against the engine's first choice** for the same position, both searched on the device at the same budget (the search for the best move starts when the position appears). Bands, in expected-score points below the first choice: best (it is the first choice), good (under 5), inaccuracy (under 10), mistake (under 20), blunder. Two exact facts override the score: allowing mate in one is a blunder; passing up a mate in one is at least a mistake. With no engine answer the move is not rated.
- **What is recorded:** mistakes and blunders are misses and return in review; best, good and inaccuracy pass; an unrated move counts for nothing. A piece left to be taken no longer needs separate proof: if the engine rates the move far below its best, it is a mistake or a blunder; if the engine accepts it, it passes, with the fact still stated. The pace ladder counts passes.
- **The result is the first thing on the screen** after a move: the rating, then "the engine rates X n points below its first choice, Y: a against b out of 100", then the facts about what can be taken, then the line to step through. A second try is offered after anything below good.
- **"How is it going?"** One-button practice has a summary at any time and at its natural end: passed of scored, and one line per kind of item (your moves by rating; questions right; missed moves found; new positions first try; due items recalled). The same summary closes the daily session. Progress shows the count behind each rating.
- Risk accepted with this: a small engine at this budget will sometimes call a sound move an inaccuracy or a mistake. The numbers are shown so that can be seen, and the outside reviewer's objection to treating one engine line as proof stands for everything that is not a rating of the engine's own score.

## ADR-044 The outside reviewer on time pressure: a fixed allowance replaces the ladder; clock figures corrected — accepted 2026-11-11
The outside reviewer answered the time-pressure question (ADR-040, ADR-041). Supersedes the pace ladder of ADR-041; the rest of ADR-041 (one loop, three checks) stands.
- **The ladder is removed.** Ten passes in twelve is too noisy to show that accuracy is reliable (a player who passes 70% of the time reaches it in about one block of twelve in four), unrated moves fell out of the count, and "pace reached" was a speed achievement in all but name. Nothing in the owner's games shows he is short of time: errors came on 92 of 886 moves (10.4%) begun with more than half the clock left and on 21 of 262 (8.0%) begun with half or less.
- **In its place: a fixed allowance on a share of positions.** About one "Your move" position in three is played with 30 seconds for choosing the move, decided by a hash of the position's id, not by how the learner is doing; the rest have no clock. Running over never forces a move and never changes the rating: the move is rated as usual and `late` is stored beside the rating (before, a passing move made late was recorded as not scored). Progress counts the two conditions apart, first looks only, with rated and unrated moves both shown. The allowance changes only by a recorded decision, which starts a new series.
- **Time is measured, not counted in ticks:** milliseconds the app was on screen in the phase, so a slow timer cannot give extra time and time in the background is not counted. The time taken to name the reply is recorded too (`reply-ms:N`).
- **Exact-fact fixes the reviewer found** (each with a test): an en passant capture takes the pawn beside the square moved to, not on it; "took what was free" is credited only when the capture played is itself one of the free ones; every reply that takes the loose piece on the stated terms, or mates, counts as naming it, not only the first found; a mate in one that no legal move prevents is not held against the move; "nothing can take back" became "nothing can take back at once", which is what is checked.
- **Clock figures in real games were wrong in one respect and are corrected.** The PGN records the clock after each move made, not at the end of the game, so a game lost on time was counted as ending with whatever the last completed move left. A loss whose termination says "on time" is counted apart as a fallen flag (5 of the owner's 29 measured rapid losses) and is never read as a clock value; for the other losses the figure is the clock "after your last completed move" (12 of those 24 had more than half left); errors are given as rates with their decision counts in both halves of the clock, not as one count. The sentence "a ten-minute game allows about 15 seconds a move" is deleted: it assumed a game length.
- **Where the owner's decision stands against the reviewer:** the reviewer would record only certified failures (exact facts) and keep engine ratings provisional. The owner asked for harder, plainer judgement (ADR-043) and that stays: engine bands decide pass or miss, with both numbers on screen.
- **The reviewer's follow-up, acted on the same day:** (a) a position is written down as shown while it is still on screen, one second after it appears, and the answer replaces that row; before, this was written on leaving the screen, which a reload or a closed app never reached, so the position could come back later as a first look; (b) an answer during which the app left the screen is marked `interrupted` and is in neither condition, because hiding the page stops the clock but not the thinking; it still counts as practice and in the ratings; (c) each condition is given as passed of every first look answered, with unrated moves in the denominator and the passed-of-rated figure beside it, so a condition cannot look better by having more unrated moves; (d) the difference between the conditions is shown with a range (Newcombe's method on the two Wilson ranges), and a range that includes nought is said to show no difference yet. At 10 to 15 timed first looks a week, only a large difference can show within several weeks.
- **Not built, recorded as open:** keeping the same position on screen across a reload (it is now recorded as shown and a different one is asked); games set aside for assessment; a time bank across several moves; comparing a prominent clock with a less salient one; the clock at moves 10, 20 and 30 of real games; resampling whole games for uncertainty; an optional "how rushed did it feel" rating.

## ADR-045 A cold UX and learnability review: the consequence on the board, one thing to do, three answers on Progress — accepted 2026-11-11
A reviewer with no earlier context used the published app before reading anything (a desktop browser window; it could not set a phone-size window or test offline, and says so). Its main finding: the app judges a move and then moves on; "the missing bridge is choose, meet the consequence, repair, choose again", and more puzzles will not supply it. What was done, in its order of importance:
- **Every mistake can be followed on the board, with one control.** The Back / On control of "Your move" is now shared (`src/ui/LineSteps.tsx`, `src/chess/line.ts`). Puzzles: the engine's answer to a wrong move opens on the board at the opponent's reply and steps back and on; a shown solution is stepped through, then "Now play it yourself" replays the position by hand (practice, the first attempt stays recorded). Own-game questions: the stored line is stepped through to where the material goes. King-and-pawn endings: "Try this position again" from the same start (practice, not recorded). The engine's expected-score number is gone from puzzle feedback; the board says it.
- **A passing rating beside "your knight can be taken" no longer reads as a contradiction.** The capture is stated as a fact about the board, apart from the rating, with what the engine does about it ("the engine does not take it" or "the engine takes it; play the line to see what you get"), and "If it is taken" plays the capture and the engine's continuation on the board. Sound moves that leave a piece attacked are still not marked wrong.
- **Today has one thing to do.** "Start training: about 30 minutes"; the other lengths, the four-block plan and the optional baseline are folded under one line. In a session the lesson stored on the device opens at once instead of a page of ways to study; leaving it shows the others. Kept against the review: "Just practise" stays on Today (the owner asked for that button there), and the play-day button keeps its fixed place (ADR-036: buttons must not move under the finger when the suggestion changes; the study/play rhythm is the route to real games).
- **Lesson steps say what is being asked:** "Find the move. The text's own move, and what it says about it, come next" instead of "play the move the text plays" when the passage naming it has not been shown. The note on how an excerpt was checked is folded into source details.
- **Progress opens on three answers:** the "Is it working?" headline (early costly mistakes in rated rapid games, rating), and what to do now. Every other number, and the data controls, are under "All the numbers, and your data"; the choice is remembered on the device. No number or denominator was removed.
- **Words:** the session summary says "New puzzles" (not "Unseen positions: None attempted" after own-game work); ending a session says what is saved instead of "cannot be reopened".
- **Not done, open:** stopping an engine line at the move where the material actually goes; letting the learner test a suspected line after a "nothing here" verdict; marking lesson steps Read / Watch / Your turn, tying each passage to the moves it describes, and holding one board orientation through a connected example (all three need the lessons re-cut and re-validated); recording the first decision of a check apart from the rest of its line; teaching the pawn ending from the permitted texts before drilling it, and playing out the defence after a failure; resuming a session after ending it; a preloaded Italian repertoire (needs the owner's own moves).
- **The reviewer's answer to what was done:** nothing in it is likely to mislead, with one guardrail, applied: an engine continuation is not automatically a refutation, and "the engine does not take it" does not show the capture is harmless; the note now says so. Its choice for the next step: stop the replay at the decisive consequence and mark it (the piece lost, the recapture that fails, the mate), in every exercise.
- **That next step, done the same day:** a replay stops where the line is decided and marks the square, with the fact in words ("Knight taken on e5. Over these moves you come out 2 points behind.", or "Checkmate."). The decisive move is the capture or promotion that first brings the material to where the line leaves it, so an even exchange that follows is not replayed; what the learner's own move took is counted. Nothing is claimed for a line that stops on a capture (the recapture may be next), an even exchange, or a line without captures: then the first six moves are shown as before. A shown solution is played to its end, with the decisive move marked on the way. It is a count of material along one engine continuation, not a judgement of the position (`consequenceOf` in `src/chess/line.ts`).
- **Process note:** these screens were changed with browser tests written alongside the change rather than before it; the two pure helpers (reading a printed line back into moves, stepping through it) were written test-first.

## ADR-046 The owner asked for his Chessreps lines to be imported: refused, and what is done instead — accepted 2026-11-11
The owner asked for "the repertoire that I use from chessreps" to be imported, "the key lines I have already as well as any recommended lines to have good coverage at my level", by opening the site in the browser. He studies four courses there by named authors (an Italian Game, an Advance Caro-Kann, a Queen's Gambit Accepted, a Fried Liver).
- **Not done, and why.** Chessreps' Terms of Service (read 2026-11-11, "last updated November 2, 2026") forbid copying or reproducing any content "except as expressly permitted", using "automated tools, bots, scrapers, or similar technology to access the Service or collect data", and using the service or anything taken from it "to build or help build a competing product or service, whether by hand or with automated or artificial-intelligence tools". The lines of a course are its content. This is the case the project's own rule was written for (membership content is linked, not mirrored; never scrape). Only the home page and the terms were opened; no course was opened and nothing was taken. The way to change this is permission from Chessreps (the owner can ask for an export of his own learned lines); until then the licensing state is "not permitted" and the app says so on the repertoire page.
- **What is done instead** (`src/openings/fromGames.ts`, `auto.ts`), from sources that are his own or open:
  1. **His own games.** In each position that his chosen moves lead to, the move he has played most, if he has played it at least twice, becomes a repertoire move marked "from your games" with its count. What he learned in a course appears because he plays it. A habit that the engine check in the opening data rates more than 8 points below the best move is not taken over; it is listed for him, and no suggestion is put in its place.
  2. **Suggestions for the common gaps.** For the unanswered positions most often reached by players of his rating band, most frequent first (at least 1% of games, at most 40 a side): the move most played in that band among those within 3 points of the engine's first choice. Marked "suggested". The margin is tighter than the 8 points that leave a habit alone, because what most players of that rating play is often playable and still not what one would recommend (the popular 5...Nxd5 against the Fried Liver is 8 points below the best move). A side with no moves from his games gets no suggestions: suggestions extend what he plays, they do not choose an opening for him.
- **Order of authority:** a move he recorded himself, then a move from his games, then a suggestion. A lower one never replaces a higher one. A suggestion gives way when his games show a habit there; entries that nothing leads to any more are removed unless he has practised them; a move he removes does not come back. In recall, a different sound move he plays against a move the app put in can be made his own with one tap, which is how a course move replaces a suggestion without the course being read.
- **It runs by itself** after games are fetched and when the repertoire page is opened, only when something it depends on has changed. Nothing is sent anywhere.
- **What it is not:** it is not his course, and it is not instruction. Suggestions are game statistics (Lichess open database, CC0) and an engine check at a small node budget; the page says so. No LLM is involved.
- On his games at the time of writing (private, not in the repository) this gives 17 moves as White and 12 as Black from his games and brings the share of games with an answer ready at his third move from 56% to 66% as White and from 24% to 53% as Black.
- Known limits: the removed-moves list is not in the backup file; the opening data is deep only after 1.e4 e5 and 1.e4 c6, so suggestions elsewhere stop early; a suggestion is asked in recall like any move, which could conflict with a course move he has not yet shown in his games (the one-tap replacement is the remedy).

## ADR-047 One set of answers: the courses decide inside their openings — accepted 2026-11-11 (owner decision)
After ADR-046 the owner said: "I want the courses to inform what moves are recommended to me. I don't want to learn two entirely different sets of responses to the same thing on two different apps. You don't have to copy the content to understand the lines." He is right about the goal, and ADR-046 fell short of it: a suggestion, or a habit read from his games, could be drilled here against what his course teaches (his games show 4.d3 against the Two Knights; a course he studies is about 4.Ng5).
- **What still cannot be done.** For the app to recommend the course's move in a position it must hold that move, and the moves of a course are its content. Reading them with this tool is "automated tools ... to access the Service or collect data", and putting them in this app is using "anything taken from" the service "to build or help build" another product "by hand or with automated or artificial-intelligence tools" (Chessreps terms, ADR-046). So the app still does not read the courses.
- **What is done: the app defers to the courses instead of competing with them** (`src/openings/courses.ts`). It knows, for each course he studies, its name, its link, the side, and which opening it is about, written as the moves that define that opening by name (the Italian after 1.e4 e5 2.Nf3 Nc6 3.Bc4, the Two Knights line of it for the Fried Liver course, the Caro-Kann after 1.e4 c6, the Queen's Gambit after 1.d4 d5 2.c4 for Black). Inside such an opening:
  1. **The app suggests nothing of its own.** Suggestions made there under ADR-046 are removed (kept only if already practised, then as moves to confirm).
  2. **A move it inferred from his games is not drilled until he confirms it.** Recall shows "Is d3 your move here?" with the count from his games, a link to the course, and the board: one tap confirms it, playing a different move makes that his move. Only then is it recalled on the schedule. The answer comes from him, never from the app.
  3. **An unanswered position points to the course**: "covered by your course The Italian Game: look the position up there and play its move here", with the link.
  4. **Games that left a move he recorded or confirmed are listed**, newest first, with "Review it in <course>" as a link. This is the way back from a real game to the course.
- Outside those openings ADR-046 stands (habits from his games; marked suggestions for common gaps).
- **What this does not do:** the app never knows a course move before he has shown it once (by confirming, by playing it on the board here, or in his games). The only route to that is an export from Chessreps with their permission, read in through the existing PGN import.
- Limits: the list of courses is in the source, not editable in the app; two of the four links go to the site's front page because the exact course pages are not recorded; territory is decided by one move order to the position, so a transposition into a course's opening by another move order is not recognised.

## ADR-048 A private copy of the backup, sent by the phone, and an audit that reads it — accepted 2026-11-11 (owner decision)
The owner asked for his recent practice to be audited (what he chose against the engine, what the app scored and said against what it should have), and then: "can you build an automatic way to get this data and review it yourself?" His practice is stored only on the phone, by design.
- **Why not something simpler.** A web app on iOS cannot write to disk or to iCloud without a tap, and a page served over HTTPS cannot reach a machine on the home network. A server of the project's own would need an account and a secret and is against "no mandatory paid API, hosting optional". The owner already has GitHub.
- **Decision.** The app can put its backup file into a private GitHub repository of the owner's (`src/db/remote.ts`). **Off by default; "local-only by default" stands.** It runs only on a device where a repository name and a token for it have been entered (Progress, Your data, "Private copy for review"). Then the same file that "Download backup" writes, gzipped, replaces `backup.json.gz` there whenever the practice data has changed, checked when the app comes to the front, when a connection returns, and once a minute while open, at most every two minutes. It is also the first copy of his progress outside the phone.
- **The token** is a fine-grained GitHub token limited to that one repository (Contents: read and write), created by the owner. It is stored in this browser's storage only; it is not in backups, not in URLs, not in the build, and is sent to `api.github.com` alone as the authorisation header. "Stop and forget the token" removes it. The repository's name (not a secret) can be built into the owner's own build so the field is filled in (`REVIEW_REPO` in the git-ignored `data/deploy.env`).
- **Reading it:** `scripts/fetch-practice.sh` pulls the latest copy into `data/remote/` (git-ignored) with the GitHub CLI.
- **The audit** (`tools/audit`, run on demand: `BACKUP=data/remote/backup.json npx vitest run -c vitest.audit.config.ts`) rebuilds each recent answer's position, replays the app's own exact checks, searches with the native engine at 1.5 million nodes a position, and reports: "Your move" answers the phone passed that the deep search fails and the reverse, with his move beside the engine's and the reply he named beside the engine's reply; whether a piece the screen called takeable is really worth taking; own-game questions whose stored answer the deep search does not support; puzzle moves recorded as misses that are as good as the solution. It judges the app, not the learner; a deep search is still an engine line. Its report is written under `data/audit/` and is private.
- The private repository (`chess-trainer-data` under the owner's account) was created by the assistant at the owner's request. The token is the owner's to create and paste: the assistant does not create credentials or change account security settings, and cannot reach the phone.
- Limits: the last minute of practice before the app is closed is sent the next time it is opened; a large history makes each send larger (the whole backup is sent each time, a few hundred kilobytes gzipped now); every send is a commit in that repository.

## ADR-049 First practice audit (10 and 11 November): what the app scored and said against a deep search — accepted 2026-11-11
The audit of ADR-048 was run on the first copy the phone sent: 99 answers over two days, each checked with the native engine at 1.5 million nodes. The report itself is private (`data/audit/`); the findings and what was changed:
- **"Your move", 11 answers.** The seven given before ADR-043 show the faults the owner had complained of: two moves that are the engine's first choice or level with it got no score at all (the old "unresolved", because a piece "could be taken"; in one case taking it would have been the opponent's mistake), and one move 13 points below the best was passed as "clean". The four given after ADR-043 agree with the deep search exactly. At the phone's node budget the current rule rates the three old cases best, good and mistake (checked with the full engine at 60,000 nodes, which is the optimistic case for the phone's smaller network).
- **Changed: "you could have taken" is no longer held against a move that was as good.** Twice the screen said a piece could have been taken for nothing while his move was the engine's first choice or 3 points from it, and Progress counted both as free pieces not taken. A free capture passed up counts as missed only when the move was rated worse than good (`freeTag`); otherwise the screen says nothing was missed.
- **Changed: "can be taken" says whether the piece is really hanging.** Twice the screen stated that a piece could be taken and nothing could take back, where the deep search rates the capture 11 and 50 points worse for the opponent than his best reply. When something can be taken after the move, the phone now also searches the position after that capture and says "it is not really hanging: taking it would be a mistake, N points worse for your opponent" or "taking it is about as good for your opponent as the engine's own reply" (`looseNote`). One more search, only in that case.
- **Changed: "Your move" uses positions from 25 to 90 out of 100, not 10 to 90.** Two of the eleven positions were nearly lost (7 and 16 out of 100 on the deep search). The ratings are bands of expected score lost, and from 16 no move can lose the 20 points that make a blunder: a move in a position at 7 was rated "good". 138 of his 167 positions remain.
- **Own-game questions, 30 answers:** the stored answer is supported by the deep search in 29. One "safe" control was wrong in what it said: king in check from a fork at 12 out of 100, the rook falls after every move, and the screen's sentence "no reply wins any material" was untrue although the move cost nothing. **Changed:** a move is offered as a "safe" control only from a position at 25 or more where the engine's best line loses no material either. One further question could not be rebuilt from the games (an item that existed when asked is no longer produced); not investigated.
- **Puzzles, 16 not solved first try:** all correctly recorded; his move cost between 39 and 96 points in each. In three the first move was right and a later one wrong; they are recorded as plain misses (already open under ADR-045).
- **Missed moves from his own games, 5 answers, 4 misses:** all correctly recorded. But this drill only printed the answer, and one position was missed on two days with two different moves. **Changed:** the engine's line and what follows his own move can be stepped through on the board, and the position can be tried again at once (practice, not recorded), as in the other exercises.
- **Observed, not changed:** of eleven items seen a second time, six were answered correctly and five missed again, one with the same wrong move; these second looks all came before the board replay existed. A missed-move drill whose answer is a queen check at move 16 was followed three minutes later by "Your move" at move 14 of the same game, where he played the same check and lost the queen: two look-alike positions from one game in one sitting. Not yet prevented.
- The audit tool was corrected in two places by its first run: for "is there something to win" a line that ends level or behind means no, and for "is it safe" a move that costs nothing against the best move is safe even when material goes anyway (it adds a note instead).

## ADR-050 Owner decision: results in one line — accepted 2026-11-11
The owner: "a lot of the result messages are way too verbose. I don't need to read a whole paragraph every time. I just want to know whether I got it right, and by how much (what was better). Only the actual useful information concisely, remove everything that is not specific to this exact case."
- **Rule for every result screen:** one line that says right or not, by how much, and what was better; after it only facts about this position, each a short line; nothing that would read the same for another position. Gone: explanations of the rating scale, "the built-in engine ... is a small one", "recorded as a pass / a miss / returns in your review queue", "exact result from the table, not an opinion", "this is the engine's line, not an explanation", the all-clear sentence when nothing can be taken, and the engine line as notation where the board control plays it.

- What a result counts as is still said where it is not obvious from the verdict (a hint, a second go, a move that could not be checked), in a few words.

## ADR-052 The result as moves on one board: you, game, best; going back; second practice audit — accepted 2026-11-12 (owner request and decisions)
The owner: "there are some cases where I'm not quite sure what I played versus what I played in the game versus what is the best line"; "it doesn't easily allow me to scroll back moves or go back puzzles, so sometimes I go forward and find no way to go back"; "can we use some visual indicator rather than explaining everything in a verbose paragraph?" His answers of 11 and 12 November (the private backup of ADR-048) were gone through: what each result screen said was rebuilt from the code and the recorded answer, and every position was checked with the native engine at 1.5 million nodes. He was shown the findings and a clickable redraw, agreed to both recommendations (the result rests on the position asked about; bars, not differences), and asked for the bars to be "very simple and intuitive".
- **What was found in the framing.** (1) In "Your move" the engine's first choice was named in the headline and never reached the board: the one playable line, labelled "Engine's line", was the engine's answer to his own move. (2) The move from the game followed a different rule in each exercise and was never rated: "Your move" named it only when it differed from the move just played, the missed-move drill only when the position was answered right. On the build of 11 November he played his game move again in 6 of 11 such answers and no screen said so. (3) The engine's first choice was "Best", "Best line", "Engine's line", "Solution" or "the winning move" depending on the exercise, and the switch between lines was "Engine's line", "After Bb5+", "Best line" or "If it is taken". (4) Nothing on the board said which line was on it: the same two arrows and "3 / 5" served every line. (5) One result named five moves in four sentences with one of them on the board. (6) Nothing went back: after "Next" a position was gone, inside a position the back arrow stopped where the shown line started, and a solved puzzle had no stepper.
- **Decision: the result is moves on one board** (`src/ui/Lines.tsx`, `mergeLines` in `src/chess/line.ts`). After an answer on a position from his own games the moves in play are chips under the board, always in the order **You, Game, Best** and always in the same three colours (amber, slate, blue; the engine's move is blue because the board is green). Two that are the same move are one chip carrying both names ("You · Game", "You · Best"). The result rests on the position that was asked, with one arrow per chip in the chip's colour. Tapping a chip plays that line on the board to where it is decided (ADR-045's rule, unchanged); tapping it again returns to the position asked. This replaces "Best was …", "In the game you played …", the two-button switches between lines, and the sentences that named a better move. It also reverses one thing in ADR-051 for these screens: a line no longer starts playing the moment the answer is given. A wrong puzzle move is still answered on the board at once, as before.
- **The bar.** Under each move, one bar: how good the position is for him after that move (the engine's expected score out of 100), fuller is better. No number is printed and nothing is subtracted; the number is in the bar's label for a screen reader and in `data-score` for tests. It replaces "13 points better". The definition stays in Progress, where the scale is explained once (ADR-050's rule).
- **The rating is a word and a mark.** "Best move.", "Good.", "Inaccuracy.", "Mistake.", "Blunder." (`gradeHeadline`) with the standard annotation beside it (★ ✓ ?! ? ??, `GRADE_MARK`), and the same mark on the corner of the square his piece stands on while his move is on the board. Own-game questions keep their one line, without notation ("Correct: O-O loses material.", "Missed: Qh5+."); the missed-move drill says "Correct.", "Missed.", "About as good: not scored.", "Shown.".
- **The moves are the stepper.** Under the chips the line on the board is written as its moves, each one a button; the one the board stands on is marked in the line's colour, and ‹ and › step either way. One step back from the first move is the position asked. This replaces "3 / 5". It puts notation back on the screen (ADR-050 took the printed engine line off): as a control this time, not as a sentence. A plain line (what a wrong puzzle move leads to, a solution, the moves of a puzzle just solved) has the same stepper without chips, so a solved puzzle can now be gone back through.
- **Facts on the board, not in sentences.** A piece of his that can be taken after his move is ringed in red with a thin arrow from what takes it, while his move stands on the board, and only when it is really hanging (`reallyLoose`: the engine's reply takes it, or taking costs the opponent under ten points, or that could not be checked). Gone from the screen: "Your knight on c3 can be taken by …", "You could have taken …", "You dealt with the threat to …", "If it is taken" and its extra line. Still said, in one small line: the reply he named beside the engine's, and "Every move allowed mate in one".

- **Going back to the last position** (`KeepLast` in `src/ui/Stage.tsx`). The run bar has a control (↩) once there is a position to go back to. It puts the previous exercise back exactly as it was left (its verdict, its chips, where each line was stepped to), to look at and step through; its main button reads "Back to where you were" and returns, and nothing is recorded a second time. The previous exercise is kept alive but not in the document, so nothing in it can be tapped by accident and nothing is on the page twice; the clock of a timed "Your move" does not run while he looks back. It works in the daily session's practice and test blocks, in review, in "Just practise" and in the practice runs for puzzles, own-game exercises and the pawn ending; it does not reach across a block change, and opening recall does not have it. The secondary action on a result ("Try again", "Try another move", "Play it yourself") moved onto the result's first line, so the pinned button is alone and the result fits a 664-point screen without scrolling.

Own-game questions, 23: the stored answer is supported in 20, doubtful in 2, unclear in 1. Puzzles not solved first try, 21: all correctly recorded. The deep search has Rd2 at 96 and the best move at 97; the phone's own record had the move costing 6 points. A position from his own games is now one item whichever exercise asks it (`src/schedule/position.ts`): one review schedule, kept under `pos:<game>:<ply>` and asked in the form it was last answered in; a first look only once; and a position met in any form is not put in front of him again as something new. Review policy v3: the states are rebuilt from the attempt log on the first open, attempts are not changed.

## ADR-053 Owner decision: the evaluation as a number at the end of each bar — accepted 2026-11-12
The owner, on seeing ADR-052 live: "Can we add like the numbers eg '+0.11' to the eval bar? But otherwise it looks good."
- **Decision.** At the end of each bar the engine's evaluation in pawns after that move is printed the way chess programs write it: "+0.11", "−2.40", "+12.3" (one decimal from ten pawns up), "0.00", and "+M" or "−M" for a forced mate (`evalText` in `src/engine/uci.ts`). This supersedes "No number is printed" in ADR-052; nothing else there changes.
- **Whose side.** The number is from the learner's side, like the bar it sits on: plus is good for him, whichever colour he has. (Chess sites print it from White's side; here the board is always turned to him and the bar already means "for you", so a number that flipped its meaning with his colour would contradict the bar.)
- **One source.** The number is computed from the same expected score the bar shows (the inverse of the conversion in `winPercent`), so the two cannot disagree, and the stored game analysis needs no new field. A stored score of exactly 100 or 0 is read as a mate; the device stores those only for forced mates and for evaluations beyond about twenty pawns.
- **Withdrawn from ADR-052: reading a result from the first moves of a line.** ADR-052 added a fallback: when the engine's whole line claimed nothing about material, its first six moves were asked on their own. A line often claims nothing because the material comes back later, and the fallback then stated a gain that the line itself takes back. It was live for about an hour in the build of `696a977`; a browser test caught it on a wrong puzzle move that took a rook ("Rook taken on h2. You end 5 points ahead.", with the replay stopped on that move and the engine's answer never shown). The rule of ADR-045 stands again unchanged: the result of a line is read from the whole line, and where that cannot be told nothing is claimed. A unit test holds a line whose capture is taken back to that. The browser test of "Your move" no longer requires the note about the knight, which depends on the engine's line: it requires that nothing else is claimed.
- **Tests.** Unit: the formatting, the round trip from an engine score, order preserved. Browser: every chip with a bar carries a number in that form, and the learner's worse move reads lower than the best one. The result still does not scroll at 390 by 664 (the chip gave up three points of padding for it).


## ADR-054 Owner request: nothing about a position before it is answered, everything after; the engine's other choices with their numbers — accepted 2026-11-15
The owner, after four days on the build of ADR-052: "it gives me too much information before I solve the puzzle (eg checkmate in one, or from your game). It should give me all the info after, with explanations. Also I would like to see the actual engine rating I get / how much I am missing by / what the best move numbers are. Just put the numbers for each line rated by the engine rounded nicely. And some of these puzzles I don't quite understand [...] the most recent puzzle I solved, I don't understand why the line with the pawn push is necessary or good [...] It would be nice to be able to see that there were better queen moves or other excellent moves that I can understand better. I wonder what the best way to create and present this information is."
- **The position he meant** (from the private copy, ADR-048): his daily game of 12 October, move 10, White, asked as "Your move" on 15 November. He played Qe4 and was shown "Inaccuracy" beside a pawn move as Best. A deep search (3 million nodes, six lines) puts h3 at +0.30, Qe3 at +0.21, Bf4 at +0.18, h4 at +0.16, a4 at +0.15 and his Qe4 at +0.10: the pawn move is not necessary, half a dozen moves are within a fifth of a pawn, and one of them is a queen move. The screen showed one "best" move, no numbers (ADR-053 was written but never published, see below) and nothing else to compare it with, so the one thing that would have answered him was not there.
- **Before the answer: whose move it is, and no more.** A puzzle said "Find the best move. Mate in one." in the practice block (the concept just studied), "Your move" said "Play your own move. Your game, Oct 12, move 10.", the missed-move drill said "One move is clearly best. Your blitz game, …", and both own-game questions named the game. All of that is gone from the question. A puzzle, "Your move" and the missed-move drill now all read "White to move" (or Black), so a position has to be looked at for what it is; the own-game questions keep their question ("Is O-O safe for White?", "Anything to win?"), which is the exercise, and lose the game. What stays before the answer is only what changes how the answer counts: the clock on a timed "Your move", "Hint used", "Second go: not recorded", and the label on a repeat opened from Progress. A run he opened himself from Practice ("Mate in 1", "Your move") still carries that name in the bar: he chose it. This reverses "show an honest heading for the concept being practised" from ADR-051 for the practice block.
- **After the answer: what it was.** Under the verdict, small and on the same line of the screen: for a position from his games, "Your daily game, Oct 12, move 10."; for a puzzle, its themes by name and its rating ("Mate in 1, Pin, rated 1465"). Tapping a puzzle's line opens each theme in words, which are Lichess's own descriptions of its puzzle themes (CC0, already in `content/themes.json`), and the link to the puzzle on Lichess. The words are a request away and not on the result by default because they do not fit above the button at 390 by 664.
- **Numbers on every line.** ADR-053's number at the end of each bar is now on puzzles too: after a wrong move, "−2.10 for you; the best move gives +5.30." (the size of what was missed, without naming the move: the attempt is already recorded as a miss); with the solution shown, the wrong move and the solution as two chips with their numbers; a solved puzzle shows its chip as "You · Solution" with the number. A solved or shown puzzle now uses the same frame as every other result (chips, then the moves), where it used to be a bare list of moves.
- **The engine's other choices** (`otherLinesFor` in `src/engine/interactive.ts`, `otherMoves` and `othersLabel` in `src/chess/line.ts`, the row in `src/ui/Lines.tsx`). Wherever moves are compared, a row under the chips shows up to three more moves from the position with their numbers, in a fourth colour (violet), each of which plays its line when tapped. They come from one search of the position for its four best moves (150,000 nodes, begun when the position appears so that it is ready with the answer), without whichever of them are already chips, in the order of their numbers. The row is headed by how they stand against that search's first choice: **About as good** when every one of them is within the "good" band of the rating (under 5 points of expected score), **Much worse** when every one would be a blunder beside it (20 or more), **Others** for anything between or mixed. A forced mate and a large advantage are the same expected score and are not called as good as each other. On his position of 12 October, in the browser here, the row reads "About as good: Bc1 +0.36, a4 +0.32, Qe3 +0.25" under Best h4 +0.42 (the phone's search can name other moves; the picture is the same).
- **They carry no rank.** The chips keep the numbers they had (the rating search, the stored analysis of the game); the row comes from a second search, and two searches at this depth need not agree on an order. So the row says "others", not "2nd, 3rd", and a move in it can read slightly higher than the chip called Best. A chip that had no number (a puzzle's solution) takes the one this search gives it. Nothing about the rating of a move changed: `gradeMove` and its two searches are as they were.
- **The row and the stepper share one place.** With the source moved into the verdict's line and the row the same height as the moves of a line, a result at rest and a result with a line open are the same height. The row is shown while the result rests on the position asked; a line on the board puts its moves there instead, and one step back from its first move brings the row back. Without this the result ran 18 to 71 points under the pinned button on a phone (measured on the first version of this change, which had the row, a sentence under it and the source on a line of its own).
- **"With explanations": what was and was not done.** What is on the screen is computed or quoted: the numbers, the other moves, the heading over them, the result of a line where it is decided (ADR-045), and Lichess's theme descriptions. No sentence is written about why a particular move is good: that would be commentary, and the project's rule is that no generated text stands in the feedback path and no instructional claim is invented. Considered and left for a later round: asking the engine what the best move threatens (the position after it with the opponent passing) and saying so only when that line wins material or mates. It costs another search per result and says nothing in a quiet position, which is the case the owner asked about; there the row of near-equal moves is the explanation. A written reason per position would need either a human author or a change to that rule, which is the owner's to make.
- **What this changes in the measurements.** From 15 November "Your move" no longer says that the position is an ordinary one from his games, and the missed-move drill no longer says that one move is clearly best. Both were information he could use; answers before and after this date were given under different instructions, and the timed-against-untimed comparison (ADR-044) and the fresh-position results should be read with that date in mind. Nothing stored was changed and no version label was bumped: the attempt's time is the marker.
- **ADR-053 had not been published.** It was written, tested and left uncommitted on a branch on 12 November; the published build stayed at `696a977`. The owner asking again for the numbers is how that was found. It is committed as `44ce0c9` and goes out with this.
- **Also changed.** "Try another move" is "Another move" (it shares a line with the source). A solved puzzle says "Solved with a hint: assisted." and "Solved after a wrong move: a miss." in place of the longer "counts as" forms, on one line with a mark. The result of a puzzle rests with the move that led to the position still marked when stepped back to its start.
- **Found on the way: a wrong puzzle move that kept what it took was never answered.** In one run of the browser suite the wrong move was fxe4, a pawn capture that the engine's whole line lets stand. The line is then "decided" on the learner's own move (ADR-045), the replay rested there, and the screen read "fxe4 is not the move. Pawn taken on e4. You end 1 point ahead." with no reply to step to. This could happen before this round; the extra search changed which line the engine gave in that test. The line that opens after a wrong puzzle move now always runs at least to the engine's answer (`replaySpan` in `src/chess/line.ts`, which holds the whole rule for how far a line is shown and where its replay rests); the sentence about the pawn is still there one step back.
- **Tests.** Unit (`src/chess/line.test.ts`): the other moves on the owner's position (compared moves left out, engine order, at most three, none twice, castling written either way, an unplayable move skipped); the three headings, the mate case, and that the bands are the rating's own; how far a line is shown and where its replay rests, with the pawn capture above. Browser: "Your move" says nothing of the game before the answer and names it after; the row has one to three moves, none of them a chip, in order of their numbers, each with a number; a tapped one plays in its own colour and its moves take the row's place; the row is back at the position asked; nothing scrolls at 390 by 664 in any of those states. A solved puzzle: "You · Solution" with "+M", themes and rating after and not before, the other moves at the start position, the themes in words on request with the Lichess link. A wrong puzzle move carries its number; with the solution shown both chips carry numbers and the solution's is higher. The practice block's puzzle does not name its concept before the answer; the own-game question does not name the game before and does after.
- **Not done.** The threat probe above. Other moves are not shown where the position asked is not his to move, or when the engine does not answer in eight seconds (the row is then absent). The heading over the row is about that row's search; where the chips come from the stored game analysis the two can disagree by a little, and nothing reconciles them. The words under "Inaccuracy" still come from bands of expected score on a small search: on the owner's position the phone called Qe4 an inaccuracy where a deep search has it a tenth of a pawn from the best move. The bands were not touched in this round. Nothing of this has been seen on the physical phone.


## ADR-055 Owner request: the result is a board to analyse on; any move tried by hand, with the engine's line after it — accepted 2026-11-17
The owner: "when I finish a puzzle/exercise and its showing me the best lines, I'd like to step through it, and have a full "analysis mode" that allows me to see, what would happen if I or they did this move instead, and what would the engine line be following that? For example, like analysis mode of chess.com. But I would like to have this worked into the existing UX so its consistent and simple and just works and allows me to fully understand the position."
- **Decision: no mode; the board on a result is live** (`useResultLines` in `src/ui/Lines.tsx`, `branchOf` in `src/chess/line.ts`). Until now the board on a result could only be watched: a chip played a line and the moves under it stepped through it. Once a position is answered a piece can now be moved on that board wherever it stands, at the position asked or any number of moves into any line, for whichever side is to move there. That is the whole of it: there is no "Analyse" button, no second screen and nothing to leave. "What if I did this instead" is making the move; "what if they did this instead" is stepping to their move and making another for them.
- **What a move made by hand does.** Three cases, decided in one function with its tests. The move the line on the board goes on with is one step on. In the position asked, the first move of a line already on the screen (a chip, or one of the engine's other choices) opens that line as its chip would. Anything else is a line of its own: the moves that led there, then the move.
- **The tried line is a fourth chip, "Try".** It stands after You, Game, Best, in the violet of the engine's other choices (ADR-054), which it is one more of: another move, with its number. It carries the same bar and the same number as the others: how good the position is for him after that move, from his side, also when the move tried was the opponent's. A move tried later than the position asked is named with its number ("Try 11." or "Try 10…"), because the other chips are all moves from the position asked and a bare "a3" would read as one more of those (seen on the first version: a3 tried on move 11 stood beside three move-10 moves). Tapping the chip opens the line on the move that was tried; tapping it again returns to the position asked, like every chip. Tried from the position asked it has its arrow there with the others.
- **The engine's line after it.** The engine is asked as soon as the move is made (one search of the position after it, the budget the exercise already uses: 40,000 nodes, or 60,000 in "Your move", the budget of its rating), its reply is played on the board at once, and its line is written under the chips as the stepper, as for any line. The replay follows the rule every line has (ADR-045, `replaySpan`): it runs on to where the line is decided if that comes after the move, marks it and says the fact ("Knight taken on e5. You end 2 points behind."); otherwise it rests on the reply, with up to six of the engine's moves written to step through. Material is counted from the position asked, along the whole line, as before. A tried move that ends the game needs no engine: mate is all or nothing, anything else a draw (`triedScore`).
- **Playing on.** A move made in a tried line tries again from there, so a position can be played out against the engine a move at a time; each move made by hand is marked in the written line, the engine's are not. Only the last try is kept: a new one replaces it, and it stays on the result (also when the position is gone back to from the bar) until then.
- **Where.** Everywhere moves are compared: "Your move", the missed-move drill, both own-game questions, and a puzzle once it is solved or its solution shown. Not after a wrong puzzle move while the puzzle is still being asked (an engine there would give the answer), and not in lessons, the pawn ending (which has its own exact table and retry) or opening recall.
- **Nothing is recorded.** A try is looking, not answering: no attempt, no rating word, no schedule. "Another move" in "Your move", "Try again" on a missed move and "Play it yourself" on a shown solution are kept: they ask the exercise again (with its reply to name, its rating, its second-go note), which a try does not.
- **Considered and not done.** A tree of variations with several tries kept (chess.com's move list): on a phone it is a second thing to navigate, and one line on the board with one try beside the three compared moves answers the question asked. The engine's several choices at every position stepped to (they are shown at the position asked, ADR-054; elsewhere the next move of the line is the engine's choice and any other can be tried). A running evaluation bar beside the board: along the engine's own line the number hardly moves, and every move made by hand gets its number on the chip. Going on past the end of a compared line with › (it still ends where it is decided, ADR-045; from there a move is made by hand and the engine goes on). A sentence or control saying that the board can be moved on: nothing was added, on the rule of less text; if it is not found, that is the first thing to add.
- **What it costs and what it can get wrong.** One more engine search per move tried, queued behind any search already running (one at a time, as before); with no answer in eight seconds the try has no number and no continuation. The number on a try comes from its own search, like the row of other moves, and can differ a little from what a chip's search would give the same move. The engine's line after a try is a small search's line, shown as the engine's and nothing more; no sentence is written about why (ADR-054's rule stands).
- **Tests.** Unit (`src/chess/line.test.ts`): the three cases of a move made by hand, for either side, with castling written either way, underpromotion as its own move, an unplayable move and a line that cannot be followed; the name of a tried move; its number from the learner's side whoever is to move, mate and stalemate without an engine; how far a tried line is shown and where its replay rests. Browser, both engines (`e2e/games.spec.ts`, `e2e/layout.spec.ts`): in "Your move" the board is movable after the answer; a move that is nowhere on the screen becomes the chip "Try" with a number, is answered on the board, and is marked in the written line where the engine's reply is not; another reply made for Black inside that line becomes "Try 10…"; the move a line goes on with, made by hand, is one step on; the chip returns to the position asked and stays; the game's move made by hand opens the game's chip; nothing moves and nothing scrolls at 390 by 664 in any of those states. A solved puzzle: another first move stands beside the solution with its number, the puzzle stays solved first try, and the mated position at the end of the solution cannot be moved on.
- **Not done.** Nothing of this has been seen on the physical phone; in particular whether a drag or two taps on the result board feels deliberate there. A tap that lands on the board right after an answer selects a piece and does nothing else, and the tap guard (ADR-036) does not cover the board.


## ADR-056 Owner report: "This review position is no longer in the installed content pack", every day — fixed 2026-11-17
The owner: "it keeps saying 'This review position is no longer in the installed content pack...' Can we fix that? Why does it happen everyday?"
- **What was found** (his private copy of 17 November, ADR-048, with the review queue rebuilt from its attempts by the app's own code): 50 items due, 12 of which review could not put on the screen. Eleven were "Your move" positions he had missed in the daily session; one was an own-game question.
- **Cause, the eleven.** "Your move" offers positions from moves 10 to 19 of a game, at least eight plies apart (`moveItems`). Review looked a due one up in the same selection made with other bounds (moves 1 to 200). The spacing is counted from the first position taken, so that list starts at the first move of the game and holds every fourth move of his from there: other positions. In one of his games the session asks plies 18, 26 and 34 and review knew 0, 8, 16, 24 and 32. Of the 147 positions the session can ask from his 88 games, review could find 23. The lookup has been so since it was written (commit `26b402f`, ADR-039), and began to matter when mistakes in "Your move" were recorded as misses (ADR-043); the fixtures of the browser tests never missed a "Your move" position and came back for it the next day.
- **Cause, the twelfth.** "Is O-O safe?" at move 21 of a game of 27 July, answered wrong on 12 November. Later the same day ADR-052 made an unsafe move one that costs ten points of expected score; this one costs 5.9, so the question no longer exists. (This is the question ADR-049 left as "could not be rebuilt from the games and was not investigated".)
- **Why every day.** An item that cannot be shown cannot be answered; the scheduler only moves an item when it is answered; so it stayed due and was announced again in every review. Each missed "Your move" position added one more.
- **Decision 1: a position that was asked is found by what it is, not by looking it up in a selection** (`moveItemById` in `src/games/ownmove.ts`). The id names the game and the move; the position, his colour and the move he played are read from the game. It does not need the game to be measured at that move, so a game being analysed again cannot make it vanish.
- **Decision 2: a position whose question is gone is asked as "Your move"** (`ownGameReview` in `src/games/reviewItem.ts`). A position from his own games is one item whichever exercise asked it (review policy v3) and comes back in the form it was last answered in; when that form can no longer be built (a question withdrawn by a later rule, a missed move that is no drill after a new analysis), the position itself is still his and is asked as "Your move", which needs only the game. The answer is recorded under that form and the same schedule goes on. Only a game that is not on the device leaves nothing to ask.
- **Decision 3: what is really gone is passed over without a word and leaves the queue.** A puzzle that a newer pack does not hold, a repertoire move since replaced, a lesson step since re-cut, a game that is not stored: there is nothing for him to do about any of these, so the card is removed. The item is marked `retired: 'gone'` in the derived review table when it comes up, so it is no longer counted as due, and the run goes on to the next item. Its attempts stay in the log. An answer recorded for it later puts it back, and opening recall treats a move marked so as new if it is in the repertoire again. A repertoire move is not called gone before the repertoire has been read (the review used to take "not read yet" for "empty").
- **Kept.** Progress still says "Position retired" on the page of an old attempt whose puzzle is not in the pack: that is a page he opened about that attempt, not something put in front of him.
- **What he will see.** Tomorrow's review holds the 13 own-game positions that are due, 12 of them for the first time since they were missed, some of them five days overdue; the review block's cap is unchanged, so they come over several days. Nothing in the attempt log or in any stored schedule was changed by this fix.
- **Tests.** Unit (`src/games/reviewItem.test.ts`): the two selections hold different positions (the cause, kept as a test); every position the session can ask is found again by its id exactly as asked, for both colours; built from the game without its measurement; nothing found for a missing game, a move past the end, the opponent's move, another kind of id; a question the games still supply is asked as it was; one they no longer supply, and a missed move that is no longer a drill, are asked as "Your move" on the same position; only a missing game leaves nothing. Browser, both engines (`e2e/games.spec.ts`): a "Your move" position missed today is the first thing in tomorrow's review, on the position that was asked; a due puzzle that the pack does not hold is not announced, is marked gone, and is not due that day or the next. Run against a build without the fix, the browser test fails where the position should appear.
- **Not done.** "N in the queue" on the Practice page still counts every item with a schedule, as it did for graduated and set-aside ones. A rebuild of the review table (a restore, a change of scheduler version) forgets which items were gone; each is marked again, silently, the first time it comes up.

The owner could not tell which positions were timed ("can we have a differentiation between the timed puzzles and non-timed … I'd like some clarity"), proposed "a fun splashy animation that says like 'timed puzzle' which will put the pressure on me", and asked whether everything should be timed instead; the aim he gave is to improve "under psychological time pressure". He was given the state of things and a recommendation, and said to build it.
- **What was there.** Only "Your move" has a clock on the move: about one position in three, 30 seconds, fixed by the position (ADR-044). It was a line of small text under the board ("30 s for this move"), and running over cost nothing. The clock in the run bar is the block's minutes, not a clock on a move. An untimed "Your move" reads "White to move" exactly as a puzzle does (ADR-054), which is intended.
- **Decision 1: announced.** A timed position opens covered: a dark slab over the whole board with a red flag reading "On the clock", the allowance as a clock face ("0:30"), and the streak when there is one. It lasts 1.3 seconds (`ANNOUNCE_MS`), counted like the clock itself, only while the exercise is on screen. The board cannot be moved on and nothing of the position can be seen until it lifts. The clock starts when the board appears, from the whole allowance; the position counts as shown from then, not from the announcement.
- **Decision 2: in sight.** While the move is chosen the clock is a bar along the board's lower edge, at the board's width, and the time beside "White to move" in large figures. Both are red for the last ten seconds (the last third of a shorter allowance, `lowAt`) and the figure beats once a second. Neither takes room: the board does not move (ADR-051), which the browser test checks. It is under the board and not in the run bar because the run bar already holds the block's minutes, and two clocks side by side was the confusion being removed.
- **Decision 3: the flag.** At nought the bar and the figure go red, with "Flag fell. Take your time: the move is still rated." The result says "Good. Flag fell at 30 s." (before: "Late: over 30 s."). What ADR-044 fixed stands: running over never forces a move and never changes its rating, and `late` is stored beside the rating.
- **Decision 4: a streak, as what the flag costs.** The run of timed first looks, newest back, that were sound (best, good or an inaccuracy) and made before the flag fell (`clockRun` in `src/schedule/pace.ts`). A mistake, a blunder or a fallen flag ends it. An unrated move, an answer during which the app left the screen, a position only shown and a second look neither add to it nor end it; an untimed position is not part of it. It is said in two places only: on the announcement ("Streak 3") and in the small line under the rating ("Streak 4." / "Streak of 4 ended."). It is not on Today or in Progress and is not stored: it is read from the attempt log.
  - *Against AGENTS.md ("the objective is not maximizing streaks").* That rule is about what the product is for. This count is a stake that makes the announced clock cost something, asked for by the owner as pressure; it counts sound moves inside the allowance and never how fast they were made (second 29 counts as second 3), so it does not bring back the speed achievement that ADR-044 removed. It is kept off every screen where it could be taken for progress. If it starts to be played for its own sake, it goes.
- **Decision 5: not everything timed.** The share stays one in three and puzzles stay untimed. (a) The untimed third is the only way to learn whether the clock costs him accuracy; with everything timed that question cannot be answered. (b) His clocks show errors made with time in hand (10.4% of moves begun with more than half the clock against 8.0% with less, ADR-044), so what is practised is doing the same check with a clock in sight, not moving faster; the check itself is built without one. (c) An announcement on every position stops being one.
- **A new series.** A clock that is felt is a different condition from a line of small text, and ADR-044 says a change starts a new series. Every "Your move" answer from this version carries `clock:2` (`CLOCK_SERIES`); answers without the tag are series 1. Progress compares timed with untimed inside series 2 only and says so ("Counted from 17 November, when the clock began to be announced and to run in sight"); series 1 is given apart in one sentence when it holds anything. The ratings (best, good, …) count every answer, whatever the clock looked like. Nothing stored was changed. The streak counts series 2 only: nothing was at stake before.
- **What it gives away.** Only "Your move" is timed, so an announced position is known to be an ordinary one from his games, where there may be nothing to find. The old clock line gave that away too; the announcement gives it away sooner. Left as it is.
- **Not established.** That practising under a visible clock carries over to his games is an inference (ADR-041), not a result. What can be read off is in Progress: timed against untimed with its range, and the rapid measures.
- **Not built (next).** A run of several positions on one clock, where the flag ends the run: the nearest thing to a game, and to his blitz, where 7 of 18 losses were on time (ADR-040). Still open from ADR-044: a rating of how rushed it felt; games set aside for assessment.
- **Tests.** Unit (`src/schedule/pace.test.ts`, 5 tests became 14): the two series are never added together and each is counted in its own; what adds to the run, what ends it, what does neither; newest back whatever the order; series 1 is not in it; the clock face rounds up and reads 0:00 only when the time is gone; when it turns red. `gradeHeadline` says "Flag fell at 30 s." Browser, both engines (`e2e/games.spec.ts`, the clock test rewritten): every state the exercise shows is noted as it changes, because the announcement and the red part of a two-second clock are too short to ask for; the announcement covers the board exactly, the board cannot be moved on and no clock exists during it; the first thing after it is the whole allowance; running, red, fallen, in that order; the board never moves; a late move keeps its rating and says the flag fell; both answers carry `clock:2`; Progress says from when it counts. 20 runs in a row on both engines passed.
- **Looked at** at iPhone size (WebKit) and on desktop, by the assistant, not by the owner: the announcement, the clock running, red, the fallen flag, both results with the streak said, and the Progress sentence.

## ADR-058 Owner request: a solution that was shown is played by hand before the run goes on — accepted 2026-11-17
The owner, while ADR-057 was being built: "when I miss a puzzle and show solution, it should always make me play it myself, never let me skip without playing it myself."
- **What was there.** After "Show solution" the main button was "Next", and "Play it yourself" was a small button beside the heading, absent in a check. On a missed move from his own games ("One move was clearly best", which since ADR-054 reads "White to move" like a puzzle), "Show the move" and a worse move both led to "Next" with "Try again" as a small button.
- **Decision: puzzles.** While a shown solution stands, the main button is "Play it yourself" and there is no "Next". The position goes back to where it was asked; "Next" appears once it has been solved by hand. Looking at the solution again during that go leaves the same debt. The second go is practice and is never recorded: the first attempt stays a miss (or assisted), as before.
- **In a check too.** ADR-051 kept the second go out of checks ("a fixed set of first tries"). The owner said always. Since the second go records nothing, it cannot change a check's result, and the browser test of an interrupted check still counts both misses.
- **Decision: his own missed moves, the same.** They are the same thing to him: one best move, shown after a miss. When the best move has been shown, whether asked for ("Shown.") or after a move the engine found clearly worse ("Missed."), the main button is "Play it yourself" or "Try again" and there is no "Next" until a move is played that is the best one or is not faulted. A first answer that was not faulted, or could not be checked, owes nothing. This is the assistant's reading of the request, not the owner's words; it is reverted by removing `owes` in `OwnGameDrill`.
- **Not changed.** "Your move" has no single answer, so "Another move" stays an offer. The yes/no questions from his games have nothing to play. The pawn ending keeps "Try again" as an offer, and so does a lesson step. Say if any of these should owe a replay too.
- **Ways out that remain.** The position gone back to with "Last" (↩) returns with its button as before. "Skip" before any answer is unchanged. Leaving the run (the way out in the bar, ending a block, a block's time running out) is always possible: nothing can hold the session.
- **Tests.** Browser, both engines: after "Show solution" there is no "Next" and "Play it yourself" stands where "Try again" stood, the board not having moved (`e2e/layout.spec.ts`); showing the solution again during the second go still gives no "Next", and solving it does (`e2e/learn-flow.spec.ts`); the same in a check, with both misses still counted; on a missed move of his own, no "Next" after a worse move, after "Show the move", or after the worse move played again, and "Next" after the best move (`e2e/games.spec.ts`).

## ADR-059 Owner request: a flag on an answered position, and a standing check for flags — accepted 2026-11-17
The owner: "I'd like a button at the end of solved puzzles that means 'flag this one for attention from claude' down the line. And write it to yourself in this repo to always check for recent issues at any request here."
- **The flag.** Once a position is answered, a flag (⚑) stands in the run bar, in the same place for every exercise: a puzzle solved or shown, "Your move", a missed move of his own, a yes/no question from his games. One tap sets it and the control turns red; a second tap takes it off. It is not there before the answer. It is the glyph alone: with a word beside it the bar of a session, which also holds the block's clock and "Skip", lost the clock. It is in the bar and not under the result because the result is already full to the pinned button on a phone, and the bar is the one place that is the same on every exercise. The position gone back to with "Last" shows its own flag.
- **What a flag keeps** (`src/db/flags.ts`): the exercise id, which exercise it was, the time, the position on the board, what the result said as text (the verdict, the chips with their numbers, the line), the exercise's state as the page carried it, and the app version. What the screen said is kept because that is what was puzzling, and the app does not store it otherwise.
- **Where it goes.** A row of the `meta` table under `flag:<exercise id>`: no schema change and no migration. It travels in the backup with the other preferences (`flag:` is a portable prefix), is restored where it is missing, and counts as something new to send to the private copy (ADR-048), so it reaches this machine without the owner doing anything.
- **Reading them** (`scripts/flags.mjs`): after `scripts/fetch-practice.sh`, lists the flags not yet handled, each with what the screen said and the answers recorded for that position; `--done <id> "<note>"` marks one handled. What was handled is kept in `data/flags-handled.json`, which like the backup is git-ignored: the repository is public and flags hold positions from his games. A flag set again after it was handled is listed again.
- **The standing check.** `CLAUDE.md` now begins every session, whatever was asked, with fetching the copy and listing the flags; each is looked at, reported to the owner, fixed if it is a defect, and marked.
- **Limits.** A flag reaches this machine only where the private copy is set up (it is, on the owner's phone) and only after the phone has sent it, which it does within a minute while the app is open and online. Nothing is sent anywhere else. Lessons, the pawn ending and opening recall have no flag yet.
- **Tests.** Unit (`src/db/flags.test.ts`): kept with what the screen said, one per position, newest first, taken off; travels in a backup; setting, replacing and removing one each change what the private copy holds, and a new flag is sent when nothing else changed. Browser, both engines: no flag before an answer; one tap keeps the position, the verdict and the moves as shown, and moves nothing on the page; a second tap removes it; the next position has none until answered; "Last" shows the earlier one flagged; a shown solution and the solved puzzle can be flagged.

## ADR-060 Owner report: "I got good, but I don't understand how the solution is possibly better"; what the engine can tell apart; positions shown and left — accepted 2026-11-17
The owner asked for his most recent position to be looked at, for how strong the engine is, and for the edge cases to be thought through: "what is truly the experience we want to give under each".
- **The position** (his daily game of 6 November, Black's move 10; he played c6 in the exercise and e6 in the game). The app said "Good" and showed e6 as "Game · Best". A search of 30 million nodes by Stockfish 19 gives e6 +0.45 to +0.70 and c6 +0.33 to +0.52 for Black: at most 4 points of expected score apart, with Qd7 between them. e6 is not meaningfully better. The screen said "Best" beside a slightly longer bar, and that is what could not be understood: there was nothing to understand.
- **How strong the engine is**, measured on his 22 "Your move" answers of 14 to 17 November. The app uses Stockfish 19 Lite at 60,000 nodes a search (depth 12 to 16; 60 ms on this Mac, more on a phone). Against the full Stockfish at 1,500,000 nodes:
  - pass or fail agreed on 22 of 22, and all 10 mistakes and blunders were confirmed (three moved one band, mistake against blunder);
  - its first choice was the deep search's in 18 of 22; in the other four several moves were within a few points of each other;
  - its numbers differ from the deep search's by about 4 points of expected score (standard deviation; up to 15 in a lopsided position), and the loss it gives a move by up to 5.
  So it is reliable for "this loses something" and far beyond any club player at that; it cannot rank moves that are within about 5 points of each other, which near equality is about a third of a pawn. A larger budget does not change this much: at 600,000 nodes its first choice matched the deep search in 16 of 22.
- **The cases, and what each should be.**
  1. *His move is the engine's first choice* (3 of 22): "Best move." Unchanged.
  2. *Another move, no difference the engine can tell* (8 of 22; at depth the gaps were 0, 0, 1, 2, 2, 3, 3 and 5 points): he should be told it was good and not be sent looking for why another move is better. **Changed:** when a move is rated good, the engine's first choice is labelled "Also good", not "Best" ("Game · Also good" when it is also the game's move). "Best" is kept for where there is a difference: an inaccuracy or worse. The numbers stay as they are.
  3. *A small real difference* (5 to 10 points, "Inaccuracy"; 1 of 22, and at depth that one was good): at the edge of what the engine can tell. It passes either way. Unchanged; it should not be read as a lesson.
  4. *A clear difference* (10 points or more; 10 of 22): reliable. "Mistake" or "Blunder", the best move shown, the position returns in review. Unchanged.
  5. *The numbers out of order* (the game's move, or his, a few hundredths above the "best"; three searches, not one): with case 2 labelled "Also good" his own move is no longer set under a "best" with a lower number. The game's chip can still stand a hair above "Best" when his move was a mistake; not changed, it claims nothing about his move.
  6. *Shown and left* (9 of his 56 positions, 16%): each was the position on screen when he stopped: he finished one, tapped "Next", and closed the app. It was recorded as seen after a second and never asked again in any form. **Changed:** such a position is owed (`owedMoves`, `movesToAsk` in `src/schedule/position.ts`): it is the first "Your move" asked next time, in a session, in "Just practise" and under Practice. Its answer is rated like any other and tagged `shown-before`; it is in neither the timed nor the untimed count and not in the streak, because it is not a first look, and Progress says how many were left out for that reason. This closes "after a reload a different position is asked rather than the same one" (ADR-044). His nine come back over the next sittings.
  7. *A lopsided position* (the position limit of ADR-049 keeps most out): in a lost position every move is "bad" and the bands say little. Seen on a fixture, not in his recent answers. Not changed.
  8. *The engine does not answer* ("Not rated"): none under the present ratings; two under the first scheme, on 10 November. Unchanged.
  9. *Yes/no questions from his games*: 14 of 17 stored answers were supported by the deep search; in two "nothing here" controls it found a pawn to win (he answered "nothing" and was marked right), one was unclear. Known since ADR-049; not changed.
  10. *Puzzles*: 8 of 8 misses confirmed; nothing to change.
- **Not built, for the owner to decide.** Saying why a move is better in words stays out (no generated text in feedback). A deeper second search for a result that is flagged or opened would cost seconds on a phone and would not change case 2. Folding "Inaccuracy" into "Good" would follow from the measurement, but he asked for hard, plain ratings (ADR-043).
- **Tests.** Unit: `src/schedule/position.test.ts` (owed while only that showing stands against it; not once answered or asked in another exercise; asked before anything new; nothing shown in this sitting is asked again in it), `src/schedule/pace.test.ts` (an answer to a position shown before is in neither condition and not in the streak, and its rating counts). Browser, both engines: a position left by a reload is the first one asked afterwards, its answer is left out of the comparison and Progress says so; a move rated good stands beside "Also good" and a worse one beside "Best".
- **Evidence.** `tools/audit` on the copy of 17 November (22 own moves, 17 questions, 8 puzzles), and the app's own engine run in a browser on the same 22 positions at 60,000 and 600,000 nodes. The figures are from his games and are kept under `data/`, not in the repository.

## ADR-061 Owner request: Progress as an app page of cards, more time series, recent games and one next action — accepted 2026-11-18
The owner asked to "redesign the progress dashboard, include more timeseries and make everything more clean concise app looking layout, and perhaps rework some of the measures", and for the design to be brainstormed with the outside designer (ChatGPT, "GPT-6 Astra"). He then wrote to it himself: "timeframes inherent into each metric", "recent game breakdowns and how we've played in different ways, and how we can improve actionably", "summarizing actions", and that each measure be explained "concise and direct and not overcrowding … visualized in an intuitive and pretty and creative way". The design and what was kept from four rounds with Astra are in `docs/superpowers/specs/2026-11-18-progress-dashboard-design.md`.
- **Supersedes the layout of ADR-045** ("Progress opens on three answers", everything else under "All the numbers"): the page has no folds and no period picker. Top to bottom: *Next up* (one action), *Recent games* (three), *In your games* (early blunders, rapid rating, big mistakes, chances taken, how you play), *In training* (spotting danger, your move, spotting chances, fresh puzzles; first looks only), *Learning* (concept checks, practice by day), *More* (rows: all time controls, retention, king-and-pawn endings, openings, play days, puzzle level, reading the ranges, your data and backup). Every card is one title, one number, one chart and one line with its sample and window, and opens a screen of its own.
- **The period picker is gone; each measure has its own windows.** One calendar window meant different reliability on every card (ten rapid games a month, nine days of training). Game charts run over game number, training charts over first looks, activity over days. Each measure's screen has *Recent / Trend / History*, defined per measure (early blunders: last 5 games / last 20 against the 20 before / all; big mistakes: last 5 / the rate over each run of 20 games / all; your move and fresh puzzles: last 20 / blocks of 20 / all; activity: 7 days / 28 / since the first answer). A window with little data is shown and marked provisional; a larger one is never put in its place.
- **The charts** (`src/ui/charts.tsx`, plain SVG, no library): games as squares (filled = an early blunder) in the last 20 against the 20 before; the rating after each rated rapid game as a line; big mistakes as the pooled rate over each run of 20 games with its 95% band and single games as faint dots; chances as one mark per clear chance; yes/no questions as two dot-and-range rows on one 0–100% axis (spotted, false alarms); "Your move" and fresh puzzles as points for consecutive blocks of 20 with their ranges, never joined, the incomplete block faint; concept checks as a grid of 29 cells by state; practice as daily bars of first looks and repeats, days before the first answer drawn flat as not recorded. A "Training" tick marks the first game on or after the day of the first attempt. Colours: one accent for series and one red for events against him, validated for colour-blind separation in light and dark (`--ch-a`, `--ch-bad`); filled against hollow carries the same meaning.
- **Measures reworked:**
  - *Big mistakes* (the major-error rate, unchanged definition) now has an interval that treats the game as the unit: the linearised standard error of a ratio with a G/(G−1) correction and t with G−1 degrees of freedom (`clusterRatio`, `src/metrics/stats.ts`). The per-decision Wilson interval treated twenty moves of one game as twenty independent observations.
  - *Chances taken* leads with the clear-chance unit already used (one move beats every other by 20 points; one chance however long it stays on the board), as a share taken rather than missed, over the last 40 rated rapid games.
  - *Your move* counts a move as sound when it was rated best, good or an inaccuracy, the verdict shown after each answer (ADR-043). Astra proposed "avoided a loss of 20 points"; not taken, so the page never disagrees with what the answer said.
  - *Spotting danger / chances*: spotted and false alarms side by side with separate denominators; never one accuracy figure.
  - *Concept checks* replace "curriculum coverage" on the page: passed, recheck due, not passed yet, studied, started, not started; a concept with no check of its own is struck through.
  - *Practice* counts positions answered per day, not minutes (an attempt left open on the screen counts as time).
  - Activity, the puzzle level and the repertoire figures are context, not outcomes, and are not ranked with the measures above.
- **New: a game breakdown** (`progress/game/<id>`): the result, the rating after, big mistakes in so many moves, chances taken; the expected score before each of his moves (the measurement record's), with the moments marked; the moments themselves, chosen by a fixed rule and each opening its position: the first early blunder, the largest big mistake, the first clear chance never taken, the first big mistake made with under a tenth of the base time (`momentsOf`). None says why a move was played.
- **New: How you play** (`progress/how`): big mistakes per 100 moves by move number (1–9, 10–19, 20–29, 30+, each with the game-clustered range), by what the move did (the four labels, counts and games), by clock (the existing rule: under 10% of the base time, undecided positions only) and by colour (with the early-blunder share), over the last 40 rated rapid games or all. Every row opens its positions.
- **New: Next up**, one action by a fixed rule: the first moment of the latest analysed rated rapid game; else positions from his games due in review; else today's training. **Not built:** Astra's "cue to carry into the next game" in fixed generic sentences — they would be teaching text written by an LLM, which `CLAUDE.md` forbids in the teaching and feedback path. The action is a link to a real position instead.
- **Kept:** the early-blunder headline definition and its comparison of the last 20 games against the 20 before (fixed in advance, ADR-027/032); every older card's numbers, moved unchanged in substance to *More* (the all-time-control rating table, errors per time control and missed chances counted every way are under "All time controls"; the long "Your move" breakdown with the clock comparison is on that measure's screen; the per-concept table on the fresh-puzzles screen). No number or denominator was removed.
- **Words:** "major error" is "big mistake" on the page (same threshold); "plausible range" is "95% range"; "provisional" is a small tag. Explanations moved off the overview into one "About this measure" per screen and one "Reading the ranges" page.
- **Caveat on the data:** 41 of his 45 rated rapid games predate training; the early-blunder screen says how many games there are since training began and that they are too few to compare.
- **Tests.** Unit: `src/metrics/stats.test.ts` (t values; the clustered ratio, wider when the same errors are bunched in one game; blocks), `src/progress/series.test.ts` (the rated rapid cohort and rating change; early blunders from the measurement record; training start; rolling rates; phase, type, colour and clock breakdowns; moments and their order; next action; first-look marks for puzzles, "Your move" and both questions; activity days not tracked before the first answer). Browser: the overview with games (next up, three recent games, cards), a game breakdown, windows on a measure, How you play; the page with no games; a card opening its screen with its windows; the backup as a row under More. The tests that used the old folds now open the screens the numbers moved to.
