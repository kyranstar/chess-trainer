# Decision log

## ADR-001 Course-first, not AI-first — accepted 2026-11-10
Use established human-written courses as the primary means of teaching new concepts. There is no generative LLM required or trusted as a correctness/education authority. Engine analysis supports concrete evaluations only.

## ADR-002 Protected-course link strategy — accepted 2026-11-10
Chess.com and Chessreps memberships provide access within the providers' interfaces. Without permission or authorized exports, link out and track completion/independent checks; do not scrape or mirror copyrighted courses. The cost is weaker integrated/offline lessons; mitigate with rights-cleared materials and explicit UX.

## ADR-003 Offline-first data, delayed sync — accepted 2026-11-10
Installable iPhone PWA with IndexedDB local progress; Mac native batch engine. Optional static hosting may deliver app shell and rights-cleared packs but cannot receive personal progress in phase 1. Explicit backup/restore is non-negotiable.

## ADR-004 Measurable performance — accepted 2026-11-10
Display separate ratings, unseen practice, reproducible game error metrics, concept mastery and cross-context transfer with denominators and source drill-down. Don't combine them into an arbitrary skill number.

## ADR-005 Deterministic scheduler first — accepted 2026-11-10
Use prerequisites, transparent priorities and memory scheduler; only introduce statistical personalization when sufficient real evidence exists, preserving unknown/uncertain states.

## ADR-006 Scope limited to one learner — accepted 2026-11-10
No login required initially, no payment system, no multiplayer/community, no shared cloud infrastructure. Private, simple, maintainable code wins over extensibility theater.

## ADR-007 Lichess board and rules libraries; project licensed GPL-3.0-or-later — accepted 2026-11-10
`@lichess-org/chessground` 10.5.0 (touch board; the unscoped `chessground` package is deprecated) and `chessops` 0.15.1 (single authoritative rules library: legality, FEN, SAN, castling, en passant, promotion, mate). Both are GPL-3.0-or-later, so this repository is GPL-3.0-or-later and any public hosting must offer the source. Alternative considered: `react-chessboard` + `chess.js` (MIT/BSD), rejected because chessground's touch handling and chessops' Lichess-compatible semantics matter more to a single-user app than licence permissiveness.

## ADR-008 Toolchain pins — accepted 2026-11-10
Node 22.23.1 (`.nvmrc`; the machine default 21.x cannot run Vite 8), React 19.3.1, Vite 8.3.7, TypeScript 7.0.2, Vitest 5.1.0, Playwright 1.65.0, Dexie 4.4.7, vite-plugin-pwa 2.0.0. `ts-fsrs` is pinned at 5.4.2, not 6.0.0, because 6.x requires Node 24 for tests; 5.4.2 already implements FSRS-6. Python 3.13 via `uv`, python-chess 1.11.2, native Stockfish 19.

## ADR-009 Local lessons are verbatim public-domain excerpts, proven mechanically — accepted 2026-11-10
Offline lessons use only text that is public domain (Edward Lasker 1918, US only; Capablanca 1921) or otherwise cleared. The app stores unaltered excerpts; `pipeline/trainer_pipeline/lessons.py` fails the build unless each paragraph is a substring of the checksummed source file, each diagram matches the book, and each move is legal and within 5 expected-score points of Stockfish's first choice. Interface prompts around a lesson are limited to facts the rules library can state ("White to move"). Cost: 1918 prose and notation, and thin coverage (see `docs/CONTENT_INVENTORY.md` §2). Excerpt selection was done by the build agent, so every lesson carries `ownerReview: pending` and the UI says so until the owner approves it. The Lasker text is cleared for the US only; a non-US owner must remove it.

## ADR-010 Puzzle answer policy and pack gate — accepted 2026-11-10
A puzzle answer is correct if it is the source move or any move that delivers checkmate (Lichess's documented rule). Everything else is scored as a miss. To make that safe, a puzzle is only shipped if Stockfish 19 (150k nodes, MultiPV 2, 1 thread) agrees at every solver move that the source move is the first choice and at least 20 expected-score points better than the second. Puzzles failing the gate are dropped, not shipped as "ambiguous". The UI therefore says "not the move" rather than "bad move", and cites the engine check.

## ADR-011 Evidence model: unseen first tries only — accepted 2026-11-10
An attempt's outcome is decided once, at the first of: wrong move (fail), hint or revealed solution (assisted), clean solve (success), or leaving before moving (skipped). `fresh` (first-ever showing) and `scheduledReview` are stamped at write time. Unseen accuracy counts fresh puzzle attempts only; assisted counts as not solved; skips are excluded and reported. Rates are shown as k of n with a 95% Wilson interval and are "provisional" below n=20. Concepts with no observations are "untested". The practice-difficulty estimate is an Elo-style number on the Lichess puzzle scale used only for selection.

## ADR-012 Concept stages and the check rubric — accepted 2026-11-10
`new → started → taught → demonstrated`, derived from lesson events. "Taught" is a finished local lesson or a self-reported linked lesson; opening a link is recorded but proves nothing. "Demonstrated" requires check-v1: 5 never-seen puzzles on the concept, Lichess rating 900–1299, no hints, 4 solved first try. Passing without a lesson is a pre-test skip. Prerequisites are advisory in the UI (nothing is locked) but the planner follows them. A fixed band, not the learner's own level, keeps "demonstrated" meaning the same thing over time.

## ADR-013 Review scheduling — accepted 2026-11-10
FSRS via ts-fsrs with fuzz off, short-term steps off, retention target 0.9 and a 365-day cap. Missed puzzles and all lesson examples enter the queue; success is Good, a miss or hint is Again. Review state is a pure fold over the immutable attempt log (`rebuildReviewStates`) and carries the scheduler version, so a scheduler change never rewrites history.

## ADR-014 Chess.com access posture — accepted 2026-11-10, two items awaiting the owner
The app never requests `www.chess.com`. Linked lessons are stored as title, author, level and URL only. Own-game import (M4) defaults to manually downloaded PGN. Open for the owner: (a) whether to keep the lesson links first collected by the automated audit or re-collect them by hand, given User Agreement §4(D); (b) whether to add a serial PubAPI fetch script for own games.

## ADR-015 Baseline is a sampler, not a score — accepted 2026-11-10
The first-run diagnostic shows two unseen positions for each of the 15 early concepts that can be assessed with positions (prerequisites ignored), choosing the least-sampled concept next. Its progress is derived from the attempt log (any unseen attempt counts), so it has no state of its own and resumes anywhere. It can only produce "untested", "provisional" or "pre-test to skip"; the 5-position check decides demonstration. A position counts for every concept whose theme tag it carries.

## ADR-016 Play days and the game journal (schema 2) — accepted 2026-11-10
A play day replaces the four study blocks with warm-up review, one 10+5 game on the learner's own site, and a written reflection. Suggestion rule v1: play after two study sessions since the last play day, never more than two play days in seven; always overridable. The game is logged by hand in `gameJournal` (schema 2: result, colour, own-words notes, optional rating and link; the link is stored and never fetched). Backups are schema 2 and still restore schema-1 files. The app writes no chess advice on the play screen. The projection in Learn assumes Wednesdays and Saturdays; real suggestions follow the rule above.

## ADR-017 An engine disagreement demotes a lesson example from "asked" to "shown" — accepted 2026-11-10
When the validator finds the author's move more than 5 expected-score points below the engine's first choice, the learner is not asked to find it; the position and the author's explanation are still shown verbatim. The text is never edited to agree with the engine, and the engine's preference is not presented as instruction.

## ADR-018 Opening repertoire: the learner's own moves, ordered by real frequency (schema 3) — accepted 2026-11-10
Chessreps has no export and its lines may not be copied, so the repertoire trainer stores only what the learner enters: for a position where it is their move, the move they have chosen (`repertoire` table, keyed by side + `positionKey`, so transpositions are one decision). The app contributes evidence, not choices:
- **Frequency**: `public/packs/openings-lichess.json`, built by `pipeline/trainer_pipeline/opening_stats.py` from the first 1.5 GB of the Lichess October 2026 rated-games dump (CC0; the explorer API needs a token). Rated blitz/rapid/classical only, each move banded by the mover's rating, full tree to 4 plies and to 14 plies under 1.e4 e5 and 1.e4 c6. The learner picks the opponent rating band; the next position to record is always the unanswered one reached most often.
- **Engine**: `opening_evals.py` stores Stockfish's expected score after each listed move and for its own first choice. A chosen move within 8 points is "sound", further is "weaker" (shown with both numbers and the first choice's name; the learner may keep it), and a move without data is "unknown", never "bad".
- **Recall** is a disclosed recall mode on FSRS: only the chosen move counts as recalled; a different move is recorded with `altVerdict` (sound / weaker / unknown) and reported separately on Progress, not as a blunder.
- **Preparedness metric**: share of games (in the chosen band) with a recorded answer at the learner's k-th move, with the shares that have no answer or fall outside the data shown beside it. It measures what is recorded, not board performance.
Limits: the sample is the start of one month, not a random sample; data is deep only under two first-move families; Lichess rating bands are not Chess.com ratings.

## ADR-019 Own games: manual PGN in, Mac analysis, file import; conservative labels (schema 4) — accepted 2026-11-10
- **Import path**: the owner downloads PGN from Chess.com by hand; `pipeline/trainer_pipeline/games.py` parses it (side, result, ratings, time class from `TimeControl` using Chess.com's own boundaries, `%clk` clocks) and never contacts a chess site. Games are identified by a hash of the site's game link, so re-imports are idempotent. A PubAPI fetcher is not built (owner decision pending, ADR-014).
- **Analysis**: Stockfish 19, 200k nodes, MultiPV 2, one thread, only at the learner's own moves. Expected score is the Lichess win% sigmoid from the learner's side. Rules, all recorded in the file manifest: major error = loss >= 20 points; label "allows mate" (mate in <= 3 for the opponent) or "loses material" (>= 2 points within 5 half-moves of the engine's reply line), otherwise "unclassified"; tactical opportunity = the engine's best line mates or wins >= 2 points within 5 half-moves; missed when the move played gave up >= 10 points; a position becomes a personal drill only when the best move beats the second best by >= 20 points. No label states why a move was played.
- **Transfer to the phone**: one JSON file (`data/analysis/my-games.json`, git-ignored) imported under Progress, Your data. Private game data is never published to static hosting.
- **App**: `games` table (schema 4, in backups). Re-analysis with different engine settings replaces the stored analysis and is labelled by `analysisKey`; mixed settings are called out on the card. Metrics: rating after each game per time control; major errors per 100 analysed decisions with Wilson range, per game and per time control; missed chances out of chances available; errors under 10% of starting time versus otherwise, shown only with 30 decisions in each group. Unanalysed games are excluded from denominators, never counted as clean.
- **Drills**: own-game positions are recalled through the same FSRS queue (`exerciseKind: 'own-game'`); they are never counted as unseen puzzles.
Not built: training-to-game transfer metric (needs dated drill history against later games), PubAPI fetch, analysis of opponents' moves.

## ADR-020 Exact king-and-pawn endings from a table computed here — accepted 2026-11-10
`pipeline/trainer_pipeline/kpk.py` computes, by level-synchronous retrograde analysis with python-chess as the move generator, the result of every K+P v K position and the number of half-moves to a safe promotion with best play (`content/kpk.json`, 279 kB, bundled). It is validated against known theory (including Lasker's "only by playing K-e5"), the published count of 111,282 won positions for the pawn on files a–d, Stockfish on a random sample, and the property that best play shortens the distance by exactly one per half-move; the app-side probe is tested against the same properties. No Syzygy download or tablebase API is needed for this ending.
The app uses it for play-outs: "win it" against the longest defence and "hold it" against the most testing tries, from 480 start positions in which exactly one move keeps the result. Every learner move is judged by whether it changed the theoretical result, so feedback says "lets the win go" or "loses" as a fact and lists the moves that kept it; nothing is engine opinion. A win must be converted within 30 moves and a draw held for 10. Results feed a separate "Endgame technique, exact" metric and the review queue, never the puzzle metric.
Still open in M5: basic mates and rook endings (need larger tables or Syzygy), exchange-counting drills, deeper calculation training, the training-to-game transfer metric, and a controlled evaluation of scheduler changes.

## ADR-021 "The opposition" is checked by exact play-outs; scheduler forecast is compared with outcomes — accepted 2026-11-10
- `endgame.opposition` no longer uses puzzles tagged "pawn endgame" as its check or its evidence. Its check is check-kpk-v1: five unseen king-and-pawn starts (three to win, two to hold) against perfect play, no help, four must be kept correct on every move. Its evidence is first-time play-outs. `endgame.passed-pawn` still uses tagged puzzles.
- `reviewCalibration` replays the attempt log and, at each scheduled review, compares the recall probability FSRS predicted just before it with the outcome. The retention card shows forecast against observed with n. This is the baseline any later scheduler version must be replayed against on the same log before it replaces v1. Note from building it: after a first miss the earliest review is one day later, which FSRS itself forecasts at about 77%, below its 90% target for established items.

## ADR-023 Game analysis v2: chances and labels measured on whole lines — accepted 2026-11-10
Running v1 on the owner's 87 real games showed two faults in the labels. v2 fixes them: a tactical chance needs the engine's best line to end at least two points up on the balance before the opponent's last move, so taking back a piece is not a chance; "loses material" means the line after the move played ends at least two points down on the balance before that move, so an even trade is not a loss; a new label "misses material" covers a major error where nothing is lost but the best line would have won at least two points more. Files carry `analysisVersion`; the app replaces a stored analysis when the version or engine settings differ.

## ADR-026 Games and ratings refresh themselves; analysis also runs in the app — accepted 2026-11-10
The owner asked that nothing about the app need a manual step ("does this automatically import all data … I don't want to have to do anything manual"). Until now the answer was no: games were fetched and analysed on the Mac and carried over as a file. This supersedes the sentence "the app still never contacts chess.com" in ADR-022 and the file-only import of ADR-019.
- When the app is opened or brought to the front (at most every three hours, or on "Refresh now") it reads the owner's public profile statistics and monthly game archives from Chess.com's Published-Data API directly from the device: documented endpoints only, strictly one request at a time, conditional requests, stop on 429, months already read are not read again except the current one. Requests carry no cookies and no referrer. The API allows cross-origin reads; this was confirmed from WebKit and Chromium on the published origin. No server of ours is involved and nothing else leaves the device.
- New games are analysed on the device by a vendored Stockfish 19 "lite, single-threaded" WebAssembly build (GPL-3.0, `public/engine/`, provenance recorded there), with the same rules as the Mac pipeline (analysis v2) at a fixed node budget. It runs only while the app is visible, newest game first, and resumes where it stopped.
- Each analysis records its engine and node budget, and the games card names the engine behind its numbers. A deeper Mac analysis becomes the analysis to look at for that game; the device's own analysis is kept beside it as the measurement record (ADR-032).
- The Chess.com handle is a preference stored on the device. The published build can carry a default handle from the git-ignored `data/deploy.env`, so the owner's phone needs no setup; the handle is then visible in the public bundle (it is the owner's public handle). It is not in the repository.
- Ratings shown are the ones Chess.com reports, with the time they were read. They are not turned into any other score.
- Failure states are explicit: offline, rate-limited, unknown player, other error; the last successful data stays in place.
The Mac pipeline and file import remain as an optional, deeper path.

## ADR-027 One game measure fixed in advance; missed chances counted where the game was still open — accepted 2026-11-10
An outside review (and an audit of the owner's 87 analysed games) found the games card flattering and unfocused. Changes:
- The headline is fixed before looking at future data: the share of rated rapid games that contain an avoidable loss of material or allowed mate within the first 20 moves, shown as the last 20 such games against the 20 before, with counts and its plausible range. Time controls are never pooled; unrated games and games against bots are left out. Its exact definition and the engine setting behind it are in ADR-032.
- "Chances missed" leads with positions that were not already decided (expected score before the move under 90), because converting a won game by another route is not a miss; the all-positions figure stays beside it.
- Clock pressure uses the clock before the move was made, not after.
- Hinted solves no longer feed the level estimate.

## ADR-028 Questions from the owner's own games: "is this move safe?" and "is there something here?" — accepted 2026-11-10
Both reviews found the largest group of the owner's real errors (about a third) to be one-move piece-safety failures, and that puzzle practice does not train noticing them, because a puzzle announces that something is there. The app now builds two kinds of question from analysed own games: a move that was played is shown and the learner says whether it is safe (then shows the punishing reply), and a position is shown and the learner says whether there is a clear chance (then plays it). Half of each kind are controls where the honest answer is "safe" / "nothing special", so always answering yes scores badly. Positives and controls are defined by the same test (ADR-032); truth comes only from stored engine analysis with fixed margins; a reply the stored analysis cannot judge is checked by the device engine, and if that is unavailable the answer is recorded as unverified, never as wrong. Hit rate on real items and the rate of false alarms on controls are reported separately. No explanatory text is written by the app. These alternate with puzzles in the unannounced test block and can be practised on their own.

## ADR-029 Checks are delayed, do not announce their theme, and are asked again — accepted 2026-11-10
Both reviews objected that a concept became "demonstrated" for good after five single-theme puzzles taken minutes after its lesson. Now: inside a session a first check is never given on the day the lesson was studied and needs at least six hours in between (a lesson at 23:55 is not checked at 00:05), and the concept that has waited longest goes first; while it runs the check does not name its concept (the result does); a passed check is asked again after 21 days. A demonstrated concept whose pass is stale, or whose re-check was not passed, is labelled as such. It keeps unlocking what depends on it, because revoking that would lock lessons already begun. The check on a concept's own page stays available at any time as the learner's choice. Fixed alongside: the five positions of a check are drawn once (they used to be re-drawn after each answer and could run out mid-check), and a check position cannot be skipped.

## ADR-030 Review rules after the audits — accepted 2026-11-10
- Due means due today (local calendar day), not "24 hours later to the minute".
- A repertoire drill is identified by position and move. Changing the move for a position starts a new item; states saved under the old position-only id are no longer offered and the position is recalled once more under its new id. Attempts are never rewritten.
- Castling is stored and looked up in one spelling.
- A position that was shown and left is recorded as skipped (so it can never count as unseen later); skipped showings do not reset "days since last seen".
- The apply block only targets concepts that have a puzzle filter; a concept checked by play-outs used to receive arbitrary puzzles.
- A session opened and left untouched does not count toward the play-day suggestion.

## ADR-031 Session identity, atomic session writes, preferences in backups, promotion in K+P v K — accepted 2026-11-10
- The running session is found by its state: an unfinished session of today, or one from yesterday still in use within the last three hours. A session in progress at midnight no longer disappears, and no empty row is written.
- Session changes are read-modify-write inside one transaction, so a clock tick and a recorded attempt cannot overwrite each other.
- Backups carry the learner's preferences (opening band and side, lesson positions, Chess.com handle) in an optional, checksummed section; device bookkeeping is not carried; a preference already set on the receiving device is kept. Every earlier backup file still restores.
- King and pawn endings: promoting to a bishop or knight, or to a queen that stalemates or can be taken, is a draw and is scored as one; when holding a draw the app's side never promotes into a capture while another move exists, and a play-out that leaves the ending ends cleanly.
- The board is measured again at the start of every touch. It used to keep its old screen position when something above it appeared, so a correct tap could be recorded as a different, wrong move.

## ADR-032 One measurement record per game; the target defined on the board; controls that mean something — accepted 2026-11-10
The outside reviewer's second pass found three faults in ADR-026 to ADR-028 as first built. All three were real.
- **A changing mix of engines would have faked a trend.** Older games analysed by the Mac's full engine and newer ones by the phone's small engine are not the same measurement. Every game now gets a measurement record: the app's own analysis (analysis v3, the vendored engine, one node budget, a fresh engine state for each game), stored beside whatever other analysis the game has. An imported Mac analysis is what you look at when reviewing a game; it never replaces the measurement record. The headline number reads only measurement records of one engine setting, names that setting, and reports games still waiting as pending. Changing the setting means re-measuring both comparison groups, not mixing.
- **The headline still depended on the score scale.** A "major error" needs a 20-point drop in expected score, and that scale flattens out in positions already won or lost: a piece hung there barely moves it. The target is now defined on the board. Analysis v3 records for every decision the expected score before it and the material balance at the end of the short line after the move played and after the best move. A target event is a move that allowed an avoidable mate in three or fewer, or lost at least two points of material that the best move would not have lost. One exception: in an undecided position (expected score 10 to 90) a move the engine rates within two points of best is a sacrifice it accepts, not an event. Beside the per-game share the card shows every such move per decision in the same move range, because "at least one per game" cannot show three mistakes becoming one. Known limit: a sound sacrifice in a position that is already decided is counted.
- **Some "safe" and "nothing special" controls were not.** A move that hung a piece in a lost position cost under three points and could be offered as safe; a position with two winning captures could be offered as nothing special. Now a safe control must lose less than two points of material in its line, allow no quick mate, cost at most three points, and come from an undecided position; a "nothing special" control needs a best line that wins less than two points of material and is not a mate. Forced losses, costly moves that lose no material, and positions with several winning moves are not asked at all. Questions are built only from measurement records.
Also from that pass: games actually played (fetched rapid, blitz and bullet games) count as play days whether or not a play session was logged; after a wrong puzzle move the built-in engine's reply can be shown on request, labelled as the engine's line and not as an explanation; a forced "Refresh now" is never dropped while a background round is running.
Not taken up: showing detection as d-prime (the reviewer advised against it at these sample sizes); a self-generated "choose a move, predict the reply, keep or revise" drill, which is the reviewer's recommended next format and is the next slice.

## ADR-033 After the data-validity audit — accepted 2026-11-10
An audit that re-ran the game pipeline on the owner's 87 games and read 53 labelled positions by hand found the following. What was changed in the app:
- **The same game did not get the same analysis twice** (5 of 87 identical between two runs): the engine's memory carried over from whatever was analysed before. The device now clears the engine before every game, and a test analyses one game twice with another in between and requires identical records.
- **Material verdicts were read off lines cut short in the middle of an exchange.** The device parser already ignores unfinished search results (bounds). In addition a line that stops right after a capture, or with captures still going on at the cut-off, is marked unsettled: such a decision is neither a target event nor a "nothing here" control.
- **Unrated games were treated as rated**: PGN files do not say, and an unrated game often carries the rating of another time control. Games fetched by the app carry the flag; a sync now also fills it in for games that arrived as a file; unrated games are left out of the rating series as well as the headline.
- **"Missed chances" mostly counted positions with nothing to find** (several moves winning about as much), and counted one chance again on every move it stayed available. The card now leads with chances that had one clearly best move (20 points over the next), each counted once and missed only if never taken.
- **The clock card pointed the wrong way**: most low-clock moves come in games already decided, where a major error is impossible. Only undecided positions are compared (from the measurement record), with the clock before the move.
Not changed, and still true of the Mac pipeline (`pipeline/trainer_pipeline/games.py`, analysis v2), which is now only the optional deeper view of a game and feeds no trend, question or headline: it does not clear the engine between games, it accepts unfinished search results, it has no "missed mate" label, and PGN downloads carry no rated flag. Also open from that audit: 10 of 27 lesson moves have another move within five points (a learner playing it is told it is not the text's move, which is true, but it is scheduled for review as a miss); one puzzle counts toward 2.4 concepts on average; Wilson intervals on decisions ignore clustering by game (the headline uses games as its unit; the secondary cards do not); the opening "sound" margin of 8 points is lenient.

## ADR-034 Owner decisions of 2026-11-10 (second set): phone only, offline on the subway, practice-heavy session — accepted
The owner answered the open questions. This narrows the product contract ("one user, iPhone and Mac" becomes one user, iPhone) and supersedes ADR-019's file import, the Mac half of ADR-022, and M6.
- **Phone only.** The Mac game route is removed: `pipeline/trainer_pipeline/games.py`, `fetch_chesscom.py`, their tests, and the in-app import of an analysed-games file. Games arrive only from Chess.com's public API and are analysed on the device. The loader for the hand-checked games fixture survives as test support (`src/games/fixtures/load.ts`). The rest of `pipeline/` stays: it builds what the phone downloads (puzzle pack, lessons, opening book, endgame table). Sync between devices (M6) is dropped; a backup file remains the way to keep a copy.
- **Offline on the subway is a hard requirement**; most sessions will happen there. Everything except fetching new games and opening linked lessons must work with no network, including the engine. A browser test now covers a cold start with no network followed by a whole session: stored games, a refresh that says plainly it is offline, an on-device lesson, own-game questions with feedback, puzzles, and the engine's reply to a wrong move. Consequence: on-device lessons for the first concepts are now the main content gap, because a linked lesson cannot be studied underground.
- **Thirty minutes is not a hard ceiling**, and the split may change. New split (planner v2): review 5, learn 8, practice 11, test 6. Practice is the largest block and alternates new positions on the concept with questions from the owner's own games, each followed by the engine's line; unused review or learn minutes go to practice. The test block stays unannounced.
- **Curriculum reordered** on the evidence of the owner's games (a third of major errors are one-move piece-safety failures; 0 of 87 games reached a pawn ending; the Caro-Kann appeared in 2 of 46 White games): hanging pieces, counting, threat scan, mate in one, opening principles, double attack, pin, defence, back rank first; pawn endings, rook endings and the Caro-Kann moved out of the first four weeks. Prerequisites are unchanged. `content/concepts.json` revision 4.
- **The 30-day projection is removed.** The owner did not know it existed, the outside reviewer advised deleting it, and its premise (a check passed on the day of the lesson) no longer holds.
- **No confirm step before a move is judged.**

## ADR-035 Ten more on-device lessons; a move as good as the text's is not a miss — accepted 2026-11-10
Because sessions happen underground (ADR-034), the first concepts of the curriculum needed lessons that are on the device. Ten lessons were added from the two cleared public-domain books (eight from Lasker 1918, two from Capablanca 1921), by the same rules as before: every paragraph is a verbatim excerpt, every position is a diagram parsed from the e-text or reached by replaying the text's moves, and every move the learner is asked for passed the engine gate. The first seven concepts in the order of ADR-034 now all have an on-device lesson (15 lessons, 13 of 29 concepts).
- Capablanca's e-text has no machine-readable diagrams, only placeholders, so its lessons use only positions replayed from the starting position; his "simple mates", "winning positions" and endings could not be used. His text is in descriptive notation and is shown as printed, with a short key.
- One book move failed the engine gate and is shown, not asked (Lasker's Diagram 33, 1.R-g3). An eleventh drafted lesson, on the back rank, was not adopted: Lasker never teaches that mate as a topic and the excerpt would have misrepresented him.
- Titles, locators and notation keys are the only words not from the books.
- **A sound move that is not the text's is not a miss.** The validity audit found other moves within the gate's five points in many lesson examples. The validator searches the engine's top candidates exactly as it searched the text's move and records those that pass. (Superseded in part by ADR-036: the app no longer calls such a move "as good" and no longer moves the lesson on.) The engine is cleared before each lesson so the evidence does not depend on the order of lessons.
- All on-device lessons remain `ownerReview: pending`.

## ADR-036 After the owner's bug report and four fresh reviews — accepted 2026-11-10
The owner found, by using the app, that an own-game question was replaced before he could answer. Cause: the practice screen chose its question again whenever the games table changed, which on a phone is every few seconds while games are analysed. No audit had looked at that code (it was written after them) and every test ran with analysis finished. Four independent reviews of the code written since the audits followed (screens under changing data; a two-week walk-through at phone size; the logic; the lessons read as a learner). Changes so far:
- **A question on screen is chosen once.** The practice screen latches its question for the turn; a browser test has a new game arrive mid-question.
- **Sync.** Every month from the one that was newest at the last complete pass is read again, so games finished late in a month are no longer lost once a newer month exists. A changed username removes the previous player's games. A game is dated by the learner's own calendar day (Chess.com's tags are UTC; an evening game in the US was dated tomorrow). One unreadable month no longer blocks later months; an internal fault is no longer reported as "offline"; after "too many requests" automatic refreshes wait an hour. If the engine does not start within 30 seconds the screen says so.
- **Own-game questions.** A reply or move other than the stored one is judged by what it does on the board (mate, or material at the end of a settled engine line), not by the expected score, which in a decided game accepted any quiet move. Another mate in one needs no engine. Controls now require that no material at all is won or lost (a pawn is neither asked nor passed off as nothing). When no question with something in it is left, none is asked. A question shown and left is recorded as skipped. The practice block's last question is not asked again in the test block. A timed-out engine search can no longer answer the next question.
- **Lessons.** The message "as good by the engine's check" contradicted the book in seven lessons (for example a move accepted right after Lasker explains why it is inferior, and in won positions where almost every move passes). Now a move the engine check does not fault (recorded at build time, or checked on the device with the same margin) is said to be not faulted, nothing is recorded against the learner, and the text's move is still asked. The lessons themselves are being re-cut by the reviewer's list: a refuted claim removed from the pin lesson, answers no longer given away, judgement calls shown instead of asked. The app's own sentences about lessons no longer overclaim ("the text is unaltered", "moves agree with Stockfish").
- **Numbers.** A chance taken by castling was counted as missed (two spellings of one move). A move counted as an early blunder was described as "not a major error" on its own page.
- **More from the same four reviews (same day).**
  - *Screens under changing data.* The decision whether a check opens the test block is taken once on entering it (a check falling due on a later clock tick replaced the puzzle on screen). The two start buttons on Today keep their places; only the emphasis follows the suggestion (they swapped under the finger when a fetched game changed it). A session finished after midnight shows its summary. The review queue looks an own-game item up once per position. When a block is closed because its time is up, nothing new is put on screen in between. The reviewer's harness (24 browser tests that drive every flow while games are fetched and analysed, clocks run out and midnight passes) is kept in `e2e-churn/` and run with `npm run e2e:churn`.
  - *Double taps.* A second tap on the same spot used to act on the next screen: it answered the next question unseen, pressed "Show the move", or ended a block. Action buttons now stay disabled for 400 ms after the screen changes (`src/app/tapGuard.ts`).
  - *A check survives a reload.* Answers already given count when the check is reopened within two hours; before, a reload (which iOS does to an app left in the background) let a check with misses be passed on five fresh positions.
  - *Lessons on the phone come first,* online or not. A concept that only has linked lessons no longer holds up the on-device lessons behind it; it is named as waiting and can be opened from Learn. It is offered in the session only when online and nothing on the device is ready.
  - *Question balance.* Taking the first of a pair sorted by hash asked a control nine times in ten ("is there something here?" had something in 5 of 60). Which comes first is now a coin toss on the seed.
  - *Lessons re-cut* from the reviewer's list (16 lessons, 50 asked moves): the refuted claim is out of the pin lesson; answers are no longer given away in the lead-in; where the text itself argues against the natural alternatives, or any winning move would do, the position is shown instead of asked (the passed-pawn and exchange lessons now have nothing to find); the opening lesson is split in two; one Capablanca lesson was rebuilt from Example 19 alone.
- **Left open from these reviews:** the review backlog grows faster than five minutes a day clears it (76 due after five simulated weeks); a reload in the practice block shows a different question and the unanswered one is not logged as seen; only the first lesson of a concept is offered by the session; the king-and-pawn check does not yet survive a reload; most concept checks (five puzzles rated 900 to 1299, for a learner whose puzzle rating is about 1600) test general puzzle strength more than the lesson; text and its diagram are on separate screens.

## ADR-037 One-button practice; the board stays with the lesson text — accepted 2026-11-10
The owner asked for "a single button that brings me into whatever I need to practise ... I shouldn't have to think about what to do and it should effectively train me best", without knowing in advance what kind of thing is coming.
- **"Just practise"** (on Today and at the top of Practice) runs an open-ended mixed stream. Policy mix-v1 (`src/schedule/mix.ts`): each turn is one of four kinds, drawn by weight from those that have something to offer: something due again (3), a question from his own games (3), an unseen position on the concept with the least evidence so far (3), a position from his own games where one move was clearly best and he played another (1). The same kind never comes three times running while another is available. Every item carries the same heading ("Practice"); no concept, theme or exercise type is announced, and puzzles are given with no hints. Each turn's item is chosen once and kept. Everything is recorded as ordinary practice: a first try on an unseen position counts as evidence, repeats do not. There is no timer and no fixed end; it stops when the learner stops or nothing is left. The weights are a first policy, to be revised with the outside reviewer's answer.
- **Due reviews are taken in order of worth**, here and in the session's review block: positions from the learner's own games first, then lesson examples, repertoire moves, endings, puzzles; longest overdue first within each.
- **In lessons the board stays at the top of the screen** while the text is read beneath it, and a page of text shows the position it is about (the board just shown, or the one that follows). Text and diagram used to be on separate screens, and on examples with a long lead-in the board started below the fold.
- From the outside reviewer's third pass (interim): the coin toss that decides whether a question has something in it was tied to the even/odd turn number through the hash's lowest bit (early "safe?" questions were all controls); the hash now has a final mixing step. A move that wins material but allows a forced mate was accepted as a chance taken; a forced mate for the other side now makes the answer wrong, and a chance taken must leave the learner at least level.
